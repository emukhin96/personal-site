# Глава 12. С нуля: порядок действий и отладка

## Зачем

Предыдущие главы разбирали готовый сайт по частям. Эта глава собирает их в план: в каком порядке
строить такой сайт самому, как проверять каждый шаг и что делать, когда что-то не работает.

Порядок важен. Каждый шаг даёт сайт, который уже собирается и открывается. Если на шаге 6 что-то сломалось,
искать причину нужно только в изменениях шага 6.

## План

| Шаг | Что делаем | Результат | Глава |
|---|---|---|---|
| 0 | Ставим Hugo extended и git | `hugo version` пишет `+extended` | 2 |
| 1 | Создаём проект и минимальный каркас | Пустая главная открывается в браузере | 2, 4 |
| 2 | Добавляем записи и шаблон записи | Записи по адресу `/posts/<адрес>/` | 3, 4 |
| 3 | Добавляем проекты и связь «запись → проект» | Хронология на странице проекта | 3, 4 |
| 4 | Выносим настройки в `data/site.yaml` | Имя и «обо мне» меняются без правки шаблонов | 3 |
| 5 | Картинки, формулы, код | WebP, `<figure>`, KaTeX без JS | 5 |
| 6 | Стили и тёмная тема | Сайт выглядит как задумано | 6 |
| 7 | `<head>`, RSS, 404 | Правильные превью в соцсетях | 7 |
| 8 | Админка | Правка из браузера | 8 |
| 9 | GitHub Actions | Сборка на каждый коммит | 9 |
| 10 | Сервер и выкладка | Сайт в интернете по HTTPS | 10, 11 |

После каждого шага: `hugo --gc --minify` без `WARN` и `ERROR`, затем коммит.

### Шаг 0. Инструменты

```bash
hugo version   # должно быть «+extended» и та же версия, что в CI
git --version
```

Как поставить Hugo и почему версия должна совпадать с CI — в главе 2.

### Шаг 1. Проект и каркас

```bash
hugo new project my-site --format yaml
cd my-site
git init
```

`hugo new project` создаёт пустые папки `archetypes/`, `assets/`, `content/`, `data/`, `i18n/`, `layouts/`,
`static/`, `themes/` и `hugo.yaml`. Флаг `--format yaml` выбирает YAML вместо TOML для настроек.
В старых версиях Hugo команда называлась `hugo new site` — это имя работает и сейчас.

Минимальный каркас: общий шаблон и главная.

```html
<!-- layouts/baseof.html -->
<!doctype html>
<html lang="ru">
<head><meta charset="utf-8"><title>{{ .Title }}</title></head>
<body>
  <main>{{ block "main" . }}{{ end }}</main>
</body>
</html>
```

```html
<!-- layouts/home.html -->
{{ define "main" }}
<h1>{{ site.Title }}</h1>
<ul>{{ range site.RegularPages }}<li><a href="{{ .RelPermalink }}">{{ .Title }}</a></li>{{ end }}</ul>
{{ end }}
```

```bash
hugo server
```

Откройте `http://localhost:1313`. Как устроены `baseof`, `block` и `define`, см. в главе 4.

**Проверено:** на этом каркасе Hugo 0.169 собирает сайт, но пишет
`WARN found no layout file for "html" for kind "section"` и то же для `"taxonomy"`.
Это нормально: шаблонов для разделов и таксономий ещё нет. Первое предупреждение исчезнет на шаге 2,
второе — после `disableKinds: [taxonomy, term]` в `hugo.yaml`, как в этом проекте (глава 2).

### Шаг 2. Записи

```bash
hugo new content posts/pervaya-zapis/index.md
```

Hugo создаёт файл по шаблону из `archetypes/default.md`:

```yaml
---
date: '2026-10-30T02:00:32Z'
draft: true
title: 'Pervaya Zapis'
---
```

Обратите внимание на две вещи.

- Файл назван `index.md` внутри папки — это **бандл страницы**: картинки записи кладутся рядом (глава 3).
- `draft: true`: обычный `hugo` черновик не опубликует, его видно только в `hugo server --buildDrafts`.

Дальше: `layouts/page.html` для одиночной страницы, `layouts/posts/section.html` для списка записей
и `permalinks` в `hugo.yaml`, чтобы адрес был `/posts/<папка>/` (главы 2–4).

**Модификация.** Чтобы `hugo new` создавал записи сразу с нужными полями, добавьте `archetypes/posts.md`:

```yaml
---
title: '{{ replace .File.ContentBaseName "-" " " | title }}'
date: '{{ .Date }}'
projects: []
summary: ''
draft: true
---
```

Hugo выбирает архетип по имени раздела: для `posts/...` возьмёт `archetypes/posts.md`, для остальных — `default.md`.
В этом проекте архетипов нет, потому что записи создаёт админка по своему описанию полей (глава 8).

### Шаг 3. Проекты и связь с записями

Порядок действий:

1. `content/projects/<адрес>/index.md` с полями `title`, `summary`, `status`, `weight`.
2. В записи — поле `projects: [<адрес-проекта>]`.
3. Partial `project-posts.html`: найти записи, у которых в `projects` есть адрес этого проекта.
4. `layouts/projects/page.html`: страница проекта с хронологией.
5. Partial `post-projects.html` и навигация «раньше / позже» в `layouts/posts/page.html`.

Почему адрес проекта — имя папки, а не название, и как работают `where ... "intersect"`, см. в главах 3 и 4.

### Шаг 4. Настройки в `data/site.yaml`

Всё, что владелец захочет поменять без программиста (имя, «обо мне», ссылки, цвет), выносится в один YAML-файл.
Шаблоны читают его через `hugo.Data.site`. На шаге 8 у этого файла появится форма в админке.

### Шаги 5–7. Картинки, стили, `<head>`

Делайте их в этом порядке. Стили проще писать, когда на странице уже есть настоящие картинки,
формулы и код. `<head>` лучше делать последним, когда ясно, какие поля есть у страниц
(`summary`, `cover`). Подробности — в главах 5, 6, 7.

### Шаги 8–10. Админка, CI, сервер

Начинайте с CI (глава 9) без задачи `deploy`: пусть сначала просто собирает сайт на каждый push.
Потом сервер (глава 10) и выкладка (глава 11). Админку (глава 8) подключайте последней:
пока нет CI, её коммиты ничего не публикуют.

## Отладка

### Инструменты Hugo

| Команда или функция | Что показывает |
|---|---|
| `hugo --logLevel info` (или `debug`) | Подробный журнал сборки |
| `hugo --printPathWarnings` | Две страницы пишутся в один и тот же файл (например, одинаковый `slug`) |
| `hugo --printUnusedTemplates` | Шаблоны, которые ни разу не использовались |
| `hugo --printI18nWarnings` | Ключи `lang.Translate`, которых нет в `i18n/` |
| `hugo --templateMetrics --templateMetricsHints` | Какие шаблоны медленные и какие стоит кешировать через `partialCached` |
| `hugo --panicOnWarning` | Остановить сборку на первом предупреждении (удобно в CI) |
| `hugo list all` / `drafts` / `future` / `expired` | Таблица страниц: путь, дата, черновик, итоговый адрес |
| `hugo config` | Итоговые настройки со всеми значениями по умолчанию |
| `{{ debug.Dump .Params }}` в шаблоне | Содержимое переменной в виде JSON прямо на странице |
| `{{ warnf "…%v" $x }}` в шаблоне | Своё предупреждение в журнал сборки |
| `{{ errorf "…" }}` в шаблоне | Остановить сборку со своей ошибкой |

**Проверено:** `hugo --printUnusedTemplates` на этом проекте пишет, что `layouts/page.html` и
`layouts/section.html` не используются. Это ожидаемо: у обоих разделов есть свои шаблоны (`posts/`, `projects/`),
а общие — запасной вариант для страниц и разделов, которые появятся позже (например, `content/about.md`).

**Проверено:** `{{ debug.Dump .Params }}` внутри `<pre>` в `layouts/posts/page.html` выводит все поля записи,
включая те, что Hugo добавил сам (`publishdate`, `lastmod`, `iscjklanguage`):

```json
{
  "date": "2026-03-02T00:00:00Z",
  "draft": false,
  "projects": ["primer-proekta"],
  "summary": "Что изменилось за два месяца.",
  "title": "Первое обновление",
  ...
}
```

### Частые ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `partial "post-lst.html" not found` с файлом и номером строки | Опечатка в имени partial'а | **Проверено.** Сообщение указывает `layouts/posts/section.html:6:3` — строку и колонку вызова |
| `mapping value is not allowed in this context` | В YAML front matter значение с `: ` внутри без кавычек, например `summary: Итог: два месяца` | **Проверено.** Взять значение в кавычки: `summary: 'Итог: два месяца'` |
| Запись не видна на сайте, но есть в `hugo server -D` | `draft: true` | Снять черновик или собрать с `--buildDrafts` |
| Запись не видна ни там, ни там | Дата в будущем | **Проверено.** По умолчанию такие записи не публикуются; `--buildFuture` их включает. Проверить: `hugo list future` |
| Запись не попала в хронологию проекта, ошибок нет | В `projects` опечатка в адресе проекта | **Проверено.** Hugo молчит: `site.GetPage` просто не находит страницу. См. упражнение 1 |
| Картинка не показывается, ошибок нет | Неверное имя файла в Markdown | **Проверено.** `resolve-image.html` не находит ресурс, и render-хук выводит обычный `<img src="chartx.png">` без обработки. См. упражнение 2 |
| `WARN Raw HTML omitted` | В Markdown есть HTML-теги, а `renderer.unsafe: false` | **Проверено.** Так и задумано (глава 5) |
| `WARN Формула не распознана` | Ошибка в LaTeX | **Проверено.** Сообщение содержит файл, строку и текст ошибки KaTeX, например `Unexpected end of input` |
| Локально всё есть, на проде ссылки ведут на `localhost` | В CI не задана переменная `SITE_URL` | Задать её (глава 9); workflow об этом предупреждает |
| На сервере старый CSS | Браузер кеширует файл | В проекте не бывает: у CSS хеш в имени (`fingerprint`, глава 6) |
| `.Site.Data was deprecated` | Старый способ читать `data/` | **Проверено** на 0.169: заменить `site.Data` на `hugo.Data` |

### Когда ничего не помогает

1. `make clean`, затем `make build`. Папка `resources/_gen/` хранит кеш обработанных картинок;
   иногда он мешает после смены настроек `imaging`.
2. `hugo server --disableFastRender`. В быстром режиме сервер пересобирает только изменённые страницы
   и может показать устаревший список. В `make dev` флаг уже стоит.
3. Сравните с рабочей версией: `git stash`, собрать, `git stash pop`. Если без ваших изменений работает —
   ищите в диффе.
4. Уменьшайте проблему: удаляйте куски шаблона, пока ошибка не пропадёт.

## Чек-лист перед публикацией

- [ ] `hugo --gc --minify` без `WARN` и `ERROR`.
- [ ] Главная, проект, запись, список записей и 404 открываются в `hugo server`.
- [ ] Проверены светлая и тёмная темы (в DevTools: Rendering → Emulate CSS prefers-color-scheme).
- [ ] Проверена ширина телефона (DevTools → устройство 360 px), нет горизонтальной прокрутки.
- [ ] Картинки отдаются в WebP, у `<img>` есть `width` и `height`.
- [ ] В `<head>` правильные `title`, `description`, `canonical` и `og:*` (глава 7).
- [ ] `public/posts/index.xml` — корректный RSS (откройте в браузере или в читалке).
- [ ] Поменяли поле во front matter — поменяли и `static/admin/config.yml` (глава 8).
- [ ] Поменяли код — поправили главу учебника, где он разобран.
- [ ] Демо-контент заменён своим.

## Упражнения: доработать проект

Это задачи на этом же репозитории. Каждая опирается на одну-две главы.

1. **Предупреждение о неизвестном проекте** (главы 3, 4). Сейчас опечатка в `projects` молча теряет запись.
   В `layouts/_partials/post-projects.html` добавьте ветку `else` к `with site.GetPage`, которая вызывает
   `warnf "Запись %s: проект %q не найден" $.File.Path .`. Тонкость: внутри `range` точка — это адрес проекта,
   а `$` — страница записи, переданная в partial.
2. **Предупреждение о пропавшей картинке** (глава 5). В `layouts/_markup/render-image.html` для пути без `://`,
   который не нашёлся как ресурс, вызовите `warnf` с `.Page.File.Path` и `.Destination`.
3. **Время чтения** (глава 4). Выведите на странице записи `{{ .ReadingTime }}` мин. Склонение «минута / минуты /
   минут» сделайте через `i18n/ru.yaml`, как у `posts`.
4. **Метки** (главы 2–4, 8). Включите таксономию `tags`: уберите `taxonomy` и `term` из `disableKinds`,
   добавьте `taxonomies: {tag: tags}`, шаблоны `layouts/taxonomy.html` и `layouts/term.html`
   и поле `tags` (виджет `list`) в админке.
5. **Переключатель темы** (глава 6). Кнопка, которая ставит `data-theme="dark"` на `<html>` и запоминает выбор
   в `localStorage`. Медиазапрос `prefers-color-scheme` должен действовать, пока пользователь ничего не выбрал.
   Это будет первый JavaScript у посетителя — решите, стоит ли он того.
6. **Поиск** (главы 1, 9). Добавьте [Pagefind](https://pagefind.app): шаг в CI после `hugo` —
   `npx pagefind --site public`, и страницу поиска с его виджетом.
7. **Архетип записи** (эта глава, шаг 2). Создайте `archetypes/posts.md` и проверьте, что `hugo new content`
   заполняет поля.

## Итог

Сайт строится слоями: каркас → контент → связи → настройки → картинки и формулы → стили → `<head>` →
CI → сервер → админка. На каждом слое сайт собирается без предупреждений, и каждый слой — отдельный коммит.
Для отладки у Hugo есть флаги `--print*`, `hugo list`, `debug.Dump` и `warnf`. Самые коварные ошибки
те, о которых Hugo молчит (опечатка в адресе проекта, неверное имя картинки), — для них стоит добавить свои
предупреждения.
