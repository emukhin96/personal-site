# Глава 1. Что строим и почему так

## Зачем

Задача: персональный сайт, на котором есть

- главная страница: имя, пара абзацев о себе, ссылки;
- список проектов, у каждого своя страница;
- записи (мини-блог) о том, как проекты создавались и менялись. Одна запись может относиться к одному
  или нескольким проектам, а на странице проекта записи сами собираются в хронологию.

Требования, которые определили весь стек:

1. **Править тексты из браузера**, без редактора кода и командной строки.
2. **Дёшево и надёжно**: сайт не должен падать от наплыва посетителей, его не должны взламывать.
3. **Быстро открываться** на телефоне со слабым интернетом.
4. **Ничего не терять**: любая правка должна сохраняться и откатываться.

## Как сделано здесь

```
Админка /admin ──коммит──▶ GitHub ──push──▶ Actions: hugo --minify ──rsync──▶ VPS (Caddy)
```

| Часть | Чем сделана | Где в репозитории |
|---|---|---|
| Генератор сайта | [Hugo](https://gohugo.io) 0.169 extended, свои шаблоны без темы | `hugo.yaml`, `layouts/` |
| Тексты | Markdown-файлы с заголовком из YAML | `content/`, `data/site.yaml` |
| Админка | [Sveltia CMS](https://sveltiacms.app): одна HTML-страница, пишет коммиты в GitHub | `static/admin/` |
| Хранилище и история | Git-репозиторий на GitHub | весь репозиторий |
| Сборка и выкладка | GitHub Actions | `.github/workflows/deploy.yml` |
| Хостинг | VPS (например, Hetzner) с веб-сервером [Caddy](https://caddyserver.com) | `deploy/` |

Что происходит, когда владелец нажимает «Сохранить» в админке:

1. Админка (JavaScript в браузере владельца) через GitHub API делает коммит в ветку `main`:
   меняет `content/posts/<адрес>/index.md` или загружает картинку.
2. GitHub видит push в `main` и запускает workflow `deploy.yml`.
3. Workflow скачивает Hugo, запускает `hugo --gc --minify` — получается папка `public/` с готовыми
   HTML, CSS и картинками.
4. Workflow копирует `public/` на сервер через `rsync` в новую папку выпуска и переключает на неё
   симлинк `current`.
5. Caddy отдаёт файлы из `/var/www/site/current`. Посетитель получает готовый HTML.

Всё вместе занимает около минуты.

## Разбор: почему именно так

### Статический сайт, а не «движок» с базой данных

Есть два способа сделать сайт.

**Динамический** (WordPress, Django, Rails). На каждый запрос посетителя сервер запускает программу,
она читает базу данных и собирает HTML. Нужны язык программирования на сервере, база данных,
обновления безопасности, резервные копии базы.

**Статический** (этот проект). HTML для всех страниц собирают один раз, заранее, на этапе сборки.
Сервер только отдаёт файлы — как флешка, доступная по сети.

| | Статический | Динамический |
|---|---|---|
| Скорость | Файл отдаётся сразу, хорошо кешируется | Каждую страницу нужно собрать (или настраивать кеш) |
| Безопасность | Нечего взламывать: на сервере нет кода, который обрабатывает ввод | Уязвимости в движке, плагинах, базе |
| Цена | Хватит самого дешёвого VPS или бесплатного хостинга | Нужно больше памяти и процессора |
| Резервная копия | Весь сайт — git-репозиторий | Файлы + дамп базы |
| Комментарии, поиск, формы | Нужны внешние сервисы или JavaScript | Есть из коробки |
| Публикация правки | Пересборка (секунды — минута) | Мгновенно |

**А если иначе.** Если бы на сайте были комментарии, личный кабинет или магазин, статический сайт пришлось бы
дополнять: комментарии — через [Giscus](https://giscus.app) (хранит их в GitHub Discussions),
форму обратной связи — через сервис форм, поиск — через [Pagefind](https://pagefind.app)
(индекс собирается вместе с сайтом и ищет прямо в браузере). Когда таких частей становится много,
проще взять динамический движок. Для визитки с блогом они не нужны.

### Hugo, а не другой генератор

Генераторов статических сайтов много. Сравнение тех, что встречаются чаще всего:

| Генератор | Язык | Чем хорош | Чем неудобен здесь |
|---|---|---|---|
| **Hugo** | Go, один файл программы | Очень быстрый, всё встроено: картинки, SCSS, формулы, RSS, sitemap | Свой язык шаблонов, к нему нужно привыкнуть |
| Jekyll | Ruby | Встроен в GitHub Pages | Медленный на больших сайтах, нужен Ruby с гемами |
| Eleventy | Node.js | Гибкий, много языков шаблонов | Обработка картинок и формул — через плагины и `node_modules` |
| Astro | Node.js | Компоненты, острова интерактивности | Сложнее, чем нужно для текстового сайта |
| Next.js | Node.js + React | Для веб-приложений | Избыточен: сайт превращается в JS-приложение |

Hugo выбран, потому что:

- **один исполняемый файл**: не нужно ставить Node.js, Ruby, сотни пакетов. В CI он скачивается одной командой
  (глава 9);
- **встроенная обработка картинок**: уменьшение и перевод в WebP при сборке (глава 5);
- **формулы рендерятся при сборке** функцией `transform.ToMath`, без JavaScript у посетителя (глава 5);
- **сборка за секунды** даже на тысячах страниц.

В CI используется сборка **extended**. Раньше только в ней были кодировщик WebP и компилятор SCSS; в Hugo 0.169
WebP умеет и обычная сборка, но локально лучше ставить ту же сборку, что в CI, чтобы результат совпадал (глава 2).

### Свои шаблоны, а не готовая тема

У Hugo тысячи [готовых тем](https://themes.gohugo.io). Тему подключают как модуль или git-подмодуль, и сайт готов за 10 минут.
Здесь тем нет: всё в `layouts/`, это около 20 небольших файлов.

- **Плюсы.** Понятно каждое место в HTML. Нет чужого кода, который сломается при обновлении темы.
  Нужная модель данных (запись → несколько проектов → хронология) встроена напрямую, а не подогнана под тему.
- **Минусы.** Всё — от `<head>` до тёмной темы — нужно написать самому. Этому и посвящены главы 4–7.

**А если иначе.** С темой структура такая же, только шаблоны лежат в `themes/<тема>/layouts/`.
Любой её файл можно переопределить, положив файл с тем же путём в свою `layouts/`:
Hugo ищет шаблон сначала в проекте, потом в теме. Так обычно и дорабатывают чужие темы.

### Админка в git, а не отдельная CMS

Варианты, как владелец правит тексты:

1. **Руками в редакторе и `git push`.** Подходит программисту, но не с телефона.
2. **Headless CMS** (Contentful, Strapi, Sanity). Тексты хранятся в базе сервиса, сайт забирает их по API при сборке.
   Удобный интерфейс, но это ещё один сервис, тарифы и данные вне репозитория.
3. **Git-CMS** (Sveltia CMS, Decap CMS). Это веб-страница, которая показывает форму и сама делает коммиты в репозиторий.
   Данные остаются Markdown-файлами в git, у каждой правки есть история.

Выбран третий вариант. Sveltia CMS — одна HTML-страница с одним скриптом, лежит в `static/admin/` и отдаётся
вместе с сайтом. Подробности — в главе 8.

### Свой VPS, а не бесплатный хостинг

Статический сайт можно бесплатно разместить на GitHub Pages, Netlify или Cloudflare Pages: они сами собирают
и раздают сайт. Здесь выбран VPS с Caddy.

| | GitHub Pages / Netlify / Cloudflare Pages | VPS + Caddy |
|---|---|---|
| Цена | Бесплатно | Несколько евро в месяц |
| Настройка | Несколько кликов | Скрипт `deploy/setup-server.sh` (глава 10) |
| Контроль | Заголовки, редиректы, кеш — в рамках возможностей сервиса | Полный: любой заголовок, любая логика Caddy |
| Откат | Зависит от сервиса | Свой механизм выпусков (глава 11) |
| Обслуживание | Нет | Обновления системы — на вас |

**А если иначе.** Перейти на GitHub Pages можно без изменения сайта: в `deploy.yml` вместо задачи `deploy`
поставить шаги `actions/upload-pages-artifact` и `actions/deploy-pages`. Шаблоны, контент и админка
от хостинга не зависят — в этом сила статического сайта.

## Принципы, которые соблюдаются во всём проекте

Они объясняют многие решения в следующих главах.

1. **Всё в git.** Тексты, настройки, картинки, конфиг сервера, скрипты выкладки. Репозиторий — это и есть сайт.
2. **У посетителя нет JavaScript.** Формулы, подсветка кода, картинки — всё готовится при сборке.
   Страница работает даже с выключенным JS.
3. **Нет внешних зависимостей у сайта.** Стили и шрифты KaTeX лежат в `static/katex/`, а не грузятся с CDN.
   Сайт не сломается, если чужой сервер недоступен, и не передаёт третьим лицам данные посетителей.
   Исключение — админка: она грузит Sveltia CMS с unpkg, но её видит только владелец.
4. **Версии зафиксированы.** Hugo — `HUGO_VERSION` в workflow, Sveltia — номер версии в URL скрипта.
   Сборка через год даст тот же результат, что сегодня.
5. **Выкладка атомарная и откатывается.** Посетитель никогда не видит наполовину скопированный сайт (глава 11).

## Где ещё пригодится

Та же схема «Markdown в git → генератор → статические файлы» подходит для документации проекта,
сайта конференции, портфолио, лендинга, базы знаний команды. Меняются только шаблоны и поля в админке.

## Упражнения

1. Откройте любой сайт на WordPress и любой сайт на Hugo (у многих в подвале написано, на чём он сделан).
   Во вкладке «Сеть» инструментов разработчика сравните время ответа сервера (TTFB) для HTML.
2. Нарисуйте свою версию схемы из раздела «Как сделано здесь» для хостинга на GitHub Pages.
   Какие шаги исчезнут, какие появятся?
3. Перечислите, какие функции вашего будущего сайта не получится сделать статическими. Чем их заменить?

## Итог

Сайт — набор готовых файлов, который собирает Hugo. Тексты — Markdown в git, их правят через страницу-админку,
которая делает коммиты. GitHub Actions собирает сайт на каждый коммит и выкладывает его на VPS,
где Caddy раздаёт файлы по HTTPS. Дальше разберём каждую часть, начиная с Hugo.
