# Глава 3. Контент

## Зачем

Контент — это всё, что пишет владелец сайта: проекты, записи, текст «обо мне». Чтобы шаблоны (глава 4)
и админка (глава 8) могли с ним работать, у контента должна быть чёткая структура:
где лежит файл, какие у него поля, как одна страница ссылается на другую.
В этой главе — как эта структура устроена и почему именно так.

## Как сделано здесь

```
content/
├── posts/
│   ├── _index.md                        страница-список «Записи»
│   ├── kak-nachinalsya-proekt/
│   │   └── index.md                     запись
│   └── pervoe-obnovlenie/
│       ├── index.md                     запись
│       └── chart.png                    картинка этой записи
└── projects/
    ├── _index.md                        страница-список «Проекты»
    └── primer-proekta/
        ├── index.md                     проект
        └── cover.jpg                    обложка проекта
data/
└── site.yaml                            имя, «обо мне», ссылки, подвал, цвет
```

Проект — `content/projects/primer-proekta/index.md`:

```markdown
---
title: Пример проекта
summary: Короткое описание в одну-две строки — оно видно в списке проектов.
status: active
started: 2026-01-15
links:
  - label: Сайт
    url: https://example.com
  - label: GitHub
    url: https://github.com/emukhin96
cover: cover.jpg
weight: 1
---
Подробное описание проекта: зачем он нужен, как устроен, что дальше.
Ниже на странице автоматически появится хронология — все записи, привязанные к проекту.

Этот проект и две записи к нему — демо-контент, их можно удалить в админке.
```

Запись — `content/posts/pervoe-obnovlenie/index.md`:

```markdown
---
title: Первое обновление
date: 2026-03-02
projects:
  - primer-proekta
summary: Что изменилось за два месяца.
---
У одного проекта может быть сколько угодно записей: они собираются в хронологию на странице проекта.

![Рост чего-нибудь](chart.png "Картинки лежат в папке записи рядом с текстом")
```

## Разбор

### Файл страницы: front matter + Markdown

Каждый файл в `content/` состоит из двух частей:

1. **Front matter** — данные страницы между строками `---`. Это YAML: пары `ключ: значение`, списки через `-`.
2. **Тело** — текст в Markdown после второй `---`.

Front matter можно писать и в других форматах — Hugo различает их по разделителю:

```toml
+++
title = "TOML-запись"
date = 2026-04-01
projects = ["primer-proekta"]
+++
```

```json
{
 "title": "JSON-запись",
 "date": "2026-04-02"
}
```

**Проверено:** обе страницы собираются, рядом с YAML-записями. Здесь выбран YAML, потому что его пишет админка
и так же записан `data/site.yaml` — один формат во всём контенте. Смешивать форматы можно, но незачем.

### Поля проекта

| Поле | Тип | Где используется | Что будет, если не указать |
|---|---|---|---|
| `title` | строка | Заголовок страницы, списки, `<title>` | Пустая строка — в списке будет ссылка без текста (**проверено** на записи: `<a href="/posts/pervoe-obnovlenie/"></a>`), ошибок нет |
| `summary` | строка | Строка под названием в списке проектов, `<meta name="description">` | Строки нет; `description` берётся из `data/site.yaml` |
| `status` | `active`, `paused`, `finished`, `archived` | Значок статуса (`_partials/status.html`) | Значка нет |
| `started` | дата | «Проект начат 15 января 2026 г.» внизу страницы | Строки нет |
| `links` | список `{label, url}` | Ссылки под заголовком проекта | Ссылок нет |
| `cover` | путь к картинке | Обложка на странице и `og:image` | Обложки нет |
| `weight` | число | Порядок проектов в списках (`.ByWeight`) | См. ниже |
| тело | Markdown | Описание проекта | Описания нет, но страница и хронология есть |

Все поля, кроме `title`, необязательны: шаблоны обёрнуты в `with`, которое просто пропускает блок, если поля нет (глава 4).

**`weight`** — ручной порядок: меньше — выше. Админка меняет его перетаскиванием (`reorder: key: weight`, глава 8).
**Проверено:** проекты с `weight: 1` и `weight: 5` и проект без `weight` выстраиваются так: 1, 5, без веса.
Страницы без веса Hugo ставит в конец, а между собой сортирует по дате и названию.

### Поля записи

| Поле | Тип | Где используется | Что будет, если не указать |
|---|---|---|---|
| `title` | строка | Заголовок, списки | Пустая ссылка |
| `date` | дата | Сортировка, группировка по годам, «раньше / позже», `<time>` | Дата нулевая — см. ниже |
| `projects` | **список** адресов проектов | Хронология проекта, ссылки на проекты | Запись есть в общем списке, но ни к какому проекту не привязана |
| `summary` | строка | Подзаголовок в списках, `description` | Подзаголовка нет |
| `cover` | путь к картинке | Обложка записи, `og:image` | Обложки нет |
| `draft` | `true` / `false` | Черновик не публикуется | `false` |

**Проверено (`date`):** без поля `date` запись получает `<time datetime="0001-01-01">1 января 1 г.</time>` и уезжает
в самый конец списков. Админка всегда ставит дату (по умолчанию — сейчас), но при ручной правке файла про неё легко забыть.

Даты в YAML пишутся как `2026-03-02` или с временем `2026-03-02T14:30:00+03:00`. Без часового пояса время
считается в UTC — для записей с точностью до дня это неважно.

### Черновики и записи «из будущего»

- `draft: true` — страница не собирается обычным `hugo`. **Проверено:** у черновика нет папки в `public/posts/`,
  а у проекта счётчик падает до «1 запись» — черновика нет нигде, даже в хронологии.
  С `hugo server -D` (так работает `make dev`) черновик виден.
- **Дата в будущем.** **Проверено:** запись с `date: 2027-01-01` не попадает в `public/` вообще, и сборка
  ничего об этом не пишет. С `--buildFuture` попадает. Это и удобно (можно «запланировать» запись —
  но она появится только при следующей сборке после этой даты, а сборка идёт только на push), и опасно:
  опечатка в годе молча прячет запись.
- Есть ещё `publishDate` (дата публикации отдельно от даты записи) и `expiryDate` (после неё страница исчезает),
  здесь они не используются.

### Markdown

Hugo превращает Markdown в HTML движком **Goldmark** — он следует стандарту CommonMark и добавляет расширения GitHub.
**Проверено:** кроме обычных заголовков, списков, ссылок, цитат и кода работают:

| Синтаксис | Результат |
|---|---|
| `\| A \| B \|` + `\|---\|:-:\|` | таблица, `:-:` — выравнивание по центру |
| `~~текст~~` | `<del>` — зачёркнутый |
| `https://example.com` в тексте | автоматически становится ссылкой |
| `- [x] сделано` | список с галочками |
| `текст[^1]` + `[^1]: сноска` | сноска внизу страницы |
| `Термин` + `: Определение` | список определений `<dl>` |
| `## Заголовок {#svoy-id}` | заголовок с заданным `id` (для ссылки `#svoy-id`) |
| `"кавычки"`, `--`, `---`, `...` | типографика: “кавычки”, –, —, … |

У заголовков `id` создаётся автоматически и сохраняет кириллицу: `## Заголовок раздела` →
`<h2 id="заголовок-раздела">`. На такой заголовок можно сослаться: `[см. выше](#заголовок-раздела)`.

**А если иначе: русские кавычки.** Типограф по умолчанию ставит английские “лапки”. **Проверено:** с настройкой

```yaml
markup:
  goldmark:
    extensions:
      typographer:
        leftDoubleQuote: '&laquo;'
        rightDoubleQuote: '&raquo;'
```

`"Кавычки"` превращается в `«Кавычки»`. В проекте этой настройки нет — можно добавить.

**А если иначе: классы у абзацев.** Атрибуты `{.класс}` по умолчанию работают только у заголовков.
**Проверено:** строка `{.lead}` после абзаца остаётся в тексте как есть; с `markup.goldmark.parser.attribute.block: true`
она превращается в `<p class="lead">`.

**HTML внутри Markdown** здесь отключён (`unsafe: false`, глава 2) — всё, что нельзя сказать Markdown'ом,
делается шаблонами или render-хуками (глава 5).

Картинки, формулы и код в Markdown разобраны в главе 5.

### Виды страниц: home, section, page

Hugo делит страницы на виды (kind), и от вида зависит шаблон (глава 4):

| Kind | Что это | Здесь | Адрес |
|---|---|---|---|
| `home` | Главная | Создаётся сама (файл `content/_index.md` не обязателен) | `/` |
| `section` | Раздел — папка первого уровня в `content/` со списком страниц | `posts`, `projects` | `/posts/`, `/projects/` |
| `page` | Обычная страница | Каждая запись и каждый проект | `/posts/pervoe-obnovlenie/` |

Также есть `taxonomy` и `term` (отключены, глава 2) и служебные `rss`, `sitemap`, `robotstxt`, `404`.

### Бандлы: `index.md` и `_index.md`

Страницу можно положить в отдельную папку вместе с её файлами — это **бандл** (bundle).

- **Leaf bundle** — папка с `index.md`. Это одна страница (kind `page`), а все остальные файлы в папке
  (`chart.png`, `cover.jpg`) — её **ресурсы**. В шаблоне до них можно дотянуться: `.Resources.Get "cover.jpg"`.
  Отсюда и простота путей: в Markdown пишется просто `![…](chart.png)`, без `/posts/…/`.
- **Branch bundle** — папка с `_index.md`. Это раздел (kind `section`), у него могут быть дочерние страницы.
  `content/posts/_index.md` задаёт заголовок раздела «Записи» и может содержать текст над списком.

Разница в одном символе `_` — и это частая ошибка.

**Проверено:** если переименовать `pervoe-obnovlenie/index.md` в `_index.md`, запись превращается в раздел:
у неё появляется собственная RSS-лента `/posts/pervoe-obnovlenie/index.xml`, она рисуется шаблоном раздела
(без даты, обложки и навигации), а счётчик у проекта падает до «1 запись» — разделы не попадают в `site.RegularPages`,
по которым ищется хронология. Ошибок сборка не выдаёт.

**А если без бандлов.** Можно писать записи файлами `content/posts/pervoe-obnovlenie.md`, а картинки класть в
`static/images/`. Так делают многие сайты, но тогда картинки лежат отдельно от текста, удаление записи оставляет
«сиротские» файлы, а главное — `static/` не обрабатывается, и картинки нельзя уменьшить (глава 5).

**Ресурсы публикуются целиком.** **Проверено:** в `public/projects/primer-proekta/` лежат и обработанные
`cover_hu_….webp`, и оригинал `cover.jpg`, хотя шаблоны используют только WebP. Чтобы не выкладывать
оригиналы (например, тяжёлые фото с камеры), в front matter страницы можно добавить

```yaml
build:
  publishResources: false
```

**Проверено:** тогда `cover.jpg` в `public/` нет, а `.webp` остаются. В проекте так не сделано: оригиналы весят немного,
а прямая ссылка на них может пригодиться.

### `_index.md` разделов

```markdown
---
title: Записи
---
```

```markdown
---
title: Проекты
outputs: [html]
---
```

- `title` — заголовок страницы-списка. **Проверено:** без `content/posts/_index.md` раздел называется по имени папки — `<h1>Posts</h1>`.
- `outputs: [html]` у проектов — только HTML, без RSS. В `hugo.yaml` разделам задано `[html, rss]`
  (глава 2), а front matter страницы сильнее общих настроек. Лента нужна для записей — на них подписываются,
  чтобы узнавать о новом. Лента проектов почти никогда не обновлялась бы. **Проверено:** без этой строки
  появляется `/projects/index.xml`.

Тело `_index.md` выводится над списком (`{{- with .Content }}` в шаблонах разделов) — сюда можно написать
вступление к разделу.

### Адреса страниц: `permalinks` и `:contentbasename`

```yaml
permalinks:
  page:
    posts: /posts/:contentbasename/
    projects: /projects/:contentbasename/
```

`:contentbasename` — имя файла без расширения, а у бандла — **имя папки**. Поэтому
`content/posts/pervoe-obnovlenie/index.md` открывается по адресу `/posts/pervoe-obnovlenie/`.

Почему это важно: адрес страницы определяется **только** именем папки. Это одно значение, которое
одновременно

- адрес страницы;
- имя папки в репозитории;
- значение, которым записи ссылаются на проект (`projects: [primer-proekta]`);
- то, что админка называет «адресом» и запрещает менять после создания (глава 8).

**А если иначе: `slug`.** В Hugo адрес можно задать полем `slug` во front matter.
**Проверено:** с `slug: update-1` у записи и текущими `permalinks` адрес остаётся `/posts/pervoe-obnovlenie/` —
`:contentbasename` не смотрит на `slug`. Если убрать блок `permalinks`, адрес становится `/posts/update-1/`.
Здесь `slug` сознательно не используется: иначе адрес и имя папки могли бы разойтись, и запись ссылалась бы
на проект по одному имени, а открывался бы он по другому.

### Данные сайта: `data/site.yaml`

```yaml
name: Ваше имя
tagline: Одна строка о том, чем вы занимаетесь
description: Персональный сайт — проекты и заметки о том, как они создавались.
about: |-
  Пара абзацев о себе. Этот текст редактируется в админке: **Настройки сайта → Обо мне**.

  Поддерживается Markdown: [ссылки](https://example.com), *курсив*, списки.
avatar: ''
links:
  - label: GitHub
    url: https://github.com/emukhin96
footer: ''
accent: '#2563eb'
```

Файл из `data/` — не страница, у него нет адреса. Это просто данные, доступные во всех шаблонах как
`hugo.Data.site` (имя файла без расширения): `hugo.Data.site.name`, `hugo.Data.site.links`.
Папки внутри `data/` становятся уровнями: `data/social/links.yaml` → `hugo.Data.social.links`.

| Поле | Где используется |
|---|---|
| `name` | Шапка, `<h1>` главной, `<title>`, подвал «© год имя» |
| `tagline` | Строка под именем на главной |
| `description` | `<meta name="description">`, если у страницы нет `summary` |
| `about` | Текст «обо мне» на главной, Markdown |
| `avatar` | Фото на главной и иконка сайта; путь вида `/uploads/photo.jpg` (глава 5) |
| `links` | Ссылки на главной |
| `footer` | Текст подвала, Markdown; пусто — «© год имя» |
| `accent` | Цвет ссылок и акцентов (глава 6) |

Детали YAML, которые здесь важны:

- `about: |-` — многострочный текст. `|` сохраняет переводы строк (а значит, абзацы Markdown), `-` убирает
  перевод строки в конце. С `>` строки склеились бы в одну и абзацы пропали бы.
- `'#2563eb'` в кавычках: без них `#` начинает комментарий, и значение было бы пустым.
- `avatar: ''` — пустая строка. Шаблон проверяет её через `with` — пустая строка считается «нет значения».

**Почему не `params` в `hugo.yaml`.** Технически имя и ссылки можно хранить в `params`. Но тогда админке
пришлось бы редактировать `hugo.yaml`, где лежат настройки сборки, и одна ошибка владельца ломала бы сайт.
`data/site.yaml` содержит только безопасные данные.

**`hugo.Data`, а не `site.Data`.** **Проверено:** старое `site.Data.site` в Hugo 0.169 работает, но печатает
`WARN deprecated: .Site.Data was deprecated in Hugo v0.156.0 and will be removed in a future release. Use hugo.Data instead.`

### Связь «запись → проекты»

Главная особенность модели данных этого сайта: запись указывает, к каким проектам относится.

```yaml
projects:
  - primer-proekta
```

Значение — **имя папки проекта** в `content/projects/`. Ссылка односторонняя: проект ничего не знает о своих записях,
Hugo находит их при сборке (шаблон `_partials/project-posts.html`, глава 4). Поэтому, чтобы добавить запись в
хронологию, достаточно создать запись — проект трогать не нужно.

Почему именно имя папки, а не название проекта:

- **Название меняется**, адрес — нет. Переименовали «Пример проекта» в «Мой первый проект» — записи не потеряли связь.
- **Название может повторяться** или содержать что угодно; имя папки уникально по определению.
- **По имени папки проект находится напрямую**: `site.GetPage "/projects/primer-proekta"`.

**Проверено:** если написать в записи `projects: [Пример проекта]` (название вместо адреса), запись молча
выпадает из хронологии: у проекта «1 запись» вместо двух, ошибок нет.

Почему **список**, а не одно значение: запись может касаться нескольких проектов сразу («перевёл оба проекта на новый
сервер»). **Проверено:** если записать одной строкой `projects: primer-proekta`, сборка падает с ошибкой
`range can't iterate over primer-proekta` в `_partials/post-projects.html` — шаблон ждёт список.
Админка всегда пишет список (`multiple: true`, глава 8).

**Что будет при переименовании папки проекта.** **Проверено:** после `mv content/projects/primer-proekta content/projects/demo`
сайт собирается без ошибок и предупреждений, но у проекта пропадает хронология, а у записей — подпись проекта:
они по-прежнему ссылаются на `primer-proekta`, которого больше нет. Поэтому админка не даёт менять адрес после создания.
Если переименовать всё-таки нужно — поменяйте значение во всех записях этого проекта
(`grep -rl 'primer-proekta' content/posts`) и учтите, что старый адрес страницы перестанет открываться
(для него можно добавить во front matter проекта `aliases: [/projects/primer-proekta/]`. **Проверено:** Hugo создаёт по старому адресу
страницу с `<meta http-equiv="refresh">` и `canonical`, которая сразу переводит на новый адрес).

**А если иначе: связь в обе стороны.** Можно было бы хранить у проекта список записей. Тогда при каждой новой записи
пришлось бы править два файла, и они легко рассинхронизировались бы. Можно было бы использовать таксономию
`projects` (Hugo сам собрал бы страницу `/projects/<имя>/` со списком записей) — но тогда у проекта не было бы своих полей
(статус, ссылки, обложка): страница термина таксономии — это прежде всего список.

## Где ещё пригодится

- Бандлы — для любой страницы со своими файлами: PDF к докладу, архив к статье, галерея.
- Связь по имени папки (`site.GetPage`) — для «автор → статьи», «серия → части», «докладчик → доклады».
- `data/` — для меню, списка публикаций, расписания, любых таблиц, которые не являются страницами.
- `draft` и `--buildDrafts` — готовить материал в основной ветке, не показывая его.

## Упражнения

1. Создайте второй проект `content/projects/vtoroy/index.md` с `weight: 2` и привяжите к нему запись
   «Первое обновление» вдобавок к первому. Где теперь видна запись?
2. Сделайте запись черновиком. Сравните `make dev` и `make build`: где она видна?
3. Поставьте записи дату на год вперёд и соберите сайт. Найдите способ увидеть её локально.
4. Добавьте в `content/posts/_index.md` абзац текста. Где он появился?
5. Добавьте в `hugo.yaml` русские кавычки и проверьте их на любой записи.

## Итог

Каждая запись и каждый проект — папка с `index.md` (leaf bundle) и своими картинками; `_index.md` — страница
раздела. Front matter в YAML несёт поля, которые используют шаблоны, тело — Markdown. Адрес страницы равен имени
папки (`:contentbasename`), и это же имя служит ссылкой из записи на проект (`projects: [...]`).
Всё, что не является страницей, но редактируется владельцем, лежит в `data/site.yaml`.
