# Глава 9. Сборка и деплой в GitHub Actions

## Зачем

После каждого коммита в `main` (из админки или руками) сайт нужно пересобрать и выложить на сервер.
Делать это вручную — значит, держать Hugo и SSH-ключ на каждом устройстве, с которого вы пишете.
**GitHub Actions** — бесплатные для публичных репозиториев (и с лимитом минут для приватных) виртуальные машины,
которые GitHub запускает по событиям в репозитории и выполняет на них ваши команды.

Ещё одна задача — **проверять pull request'ы**: если шаблон сломан, сборка упадёт в PR, а не на проде.

## Как сделано здесь

Файл `.github/workflows/deploy.yml`. GitHub сам находит все `.yml` в `.github/workflows/`.

```yaml
name: Сборка и деплой

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: false

env:
  HUGO_VERSION: 0.169.0

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - name: Установить Hugo
        run: |
          curl -fsSL -o /tmp/hugo.tgz \
            "https://github.com/gohugoio/hugo/releases/download/v${HUGO_VERSION}/hugo_extended_${HUGO_VERSION}_linux-amd64.tar.gz"
          sudo tar -xzf /tmp/hugo.tgz -C /usr/local/bin hugo
          hugo version

      - name: Собрать сайт
        env:
          SITE_URL: ${{ vars.SITE_URL }}
        run: |
          if [ -n "$SITE_URL" ]; then
            hugo --gc --minify --baseURL "${SITE_URL%/}/"
          else
            echo "::warning::Переменная SITE_URL не задана — ссылки будут на localhost. См. README → Деплой."
            hugo --gc --minify
          fi

      - uses: actions/upload-artifact@v7
        with:
          name: public
          path: public
          retention-days: 7

  deploy:
    needs: build
    if: github.event_name != 'pull_request' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v7
        with:
          sparse-checkout: deploy

      - uses: actions/download-artifact@v8
        with:
          name: public
          path: public

      - name: Выложить на сервер
        env:
          DEPLOY_HOST: ${{ secrets.DEPLOY_HOST }}
          DEPLOY_USER: ${{ secrets.DEPLOY_USER }}
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
          DEPLOY_KNOWN_HOSTS: ${{ secrets.DEPLOY_KNOWN_HOSTS }}
        run: |
          if [ -z "$DEPLOY_HOST" ]; then
            echo "::warning::Секреты деплоя не заданы — сайт собран, но не выложен. См. README → Деплой."
            exit 0
          fi
          mkdir -p ~/.ssh && chmod 700 ~/.ssh
          printf '%s\n' "$DEPLOY_SSH_KEY" > ~/.ssh/id_deploy && chmod 600 ~/.ssh/id_deploy
          printf '%s\n' "$DEPLOY_KNOWN_HOSTS" > ~/.ssh/known_hosts
          export RSYNC_RSH="ssh -i ~/.ssh/id_deploy -o IdentitiesOnly=yes"
          bash deploy/publish.sh public "$DEPLOY_USER@$DEPLOY_HOST" "${GITHUB_SHA::12}"
```

## Словарь

- **Workflow** — весь файл. Запускается по событиям из `on`.
- **Run** — один запуск workflow. Видно во вкладке **Actions** репозитория.
- **Job** (задача) — группа шагов на **отдельной чистой виртуальной машине**. Здесь две: `build` и `deploy`.
  Задачи по умолчанию идут параллельно; `needs` выстраивает их в очередь.
- **Step** (шаг) — команда (`run`) или готовое действие (`uses`). Шаги одной задачи идут по порядку на одной машине
  и видят файлы друг друга.
- **Action** — переиспользуемый шаг из другого репозитория: `actions/checkout@v7` — репозиторий
  `github.com/actions/checkout`, версия (тег) `v7`.

## Разбор

### `name` и события `on`

- **`name: Сборка и деплой`** — подпись во вкладке Actions. Без неё там будет путь к файлу.
- **`push: branches: [main]`** — запуск на каждый push в `main`: коммиты админки, слитые PR, ваши push'и.
  Push в другие ветки workflow не запускает. Можно добавить `paths:` — например, `paths-ignore: ['docs/**']`,
  чтобы правки учебника не пересобирали сайт.
- **`pull_request:`** — запуск на открытие PR и каждый новый коммит в нём. Без фильтров — для PR в любую ветку.
  Задача `deploy` для PR пропускается (см. `if`), так что PR только **проверяет сборку**.
  Важная деталь: для PR из форков GitHub не передаёт секреты — ещё одна причина не деплоить из PR.
- **`workflow_dispatch:`** — кнопка **Run workflow** во вкладке Actions. Пригодится, чтобы перевыложить сайт
  без коммита (например, после настройки сервера) или чтобы опубликовать запись с датой, которая только что наступила
  (глава 3: страницы с датой в будущем Hugo не публикует, пока сайт не пересобран).

**Где ещё пригодится:** `schedule: - cron: '0 3 * * *'` — запуск по расписанию. Так можно публиковать
отложенные записи: раз в день сайт пересобирается, и записи, чья дата наступила, появляются сами.

### `concurrency`

```yaml
concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: false
```

Запуски с одинаковой `group` не идут одновременно.

- **`${{ github.ref }}`** — выражение GitHub, подставляется до запуска. Для push в `main` это `refs/heads/main`,
  для PR № 1 — `refs/pull/1/merge`. Значит, деплои `main` выстраиваются в очередь между собой,
  а сборки разных PR друг другу не мешают.
- **`cancel-in-progress: false`** — новый запуск **ждёт**, пока текущий закончится. Если за это время
  пришло ещё несколько, GitHub держит в очереди только самый свежий, промежуточные отменяет —
  выкладывать устаревшую версию всё равно незачем.

**А если иначе:**

| Вариант | Что будет |
|---|---|
| Без `concurrency` | Два быстрых сохранения в админке → два деплоя одновременно. Оба пишут на сервер, и какой из них переключит `current` последним — вопрос удачи. Может победить более старый коммит |
| `cancel-in-progress: true` | Новый запуск убивает текущий, в том числе посреди `rsync`. Сайт не сломается — переключение выпуска атомарное (глава 11), — но на сервере останется недокачанная папка выпуска. Для деплоя «дождаться» честнее |
| `cancel-in-progress: ${{ github.event_name == 'pull_request' }}` | Компромисс: сборки PR отменяют друг друга (экономия минут), деплои `main` ждут |

### `env` уровня workflow

```yaml
env:
  HUGO_VERSION: 0.169.0
```

Переменная окружения для всех задач и шагов. Версия Hugo записана одна на весь файл: поменяли здесь —
поменялось везде. Она же — «официальная» версия проекта: `README.md` просит локально ставить ту же.

**А если иначе:** «последняя версия Hugo» (через API релизов) — сборка однажды сломается сама,
потому что вышел Hugo с изменённым поведением. В этом проекте уже есть пример: `.Site.Data` объявлен
устаревшим в 0.156, шаблоны используют `hugo.Data`. Фиксированная версия обновляется осознанно, в отдельном PR,
где сборка покажет предупреждения.

### Задача `build`

- **`runs-on: ubuntu-latest`** — образ машины. `ubuntu-latest` время от времени переезжает на новую версию Ubuntu;
  для полной воспроизводимости пишут конкретную: `ubuntu-24.04`. Для Hugo разница не важна:
  он ставится готовым файлом и от системы почти не зависит.
- **`uses: actions/checkout@v7`** — скачать репозиторий в рабочую папку. По умолчанию — только последний коммит
  (`fetch-depth: 1`). Если включить в Hugo `enableGitInfo` (дата последнего изменения страницы из git),
  понадобится вся история: `with: { fetch-depth: 0 }`.

#### Установка Hugo

```bash
curl -fsSL -o /tmp/hugo.tgz \
  "https://github.com/gohugoio/hugo/releases/download/v${HUGO_VERSION}/hugo_extended_${HUGO_VERSION}_linux-amd64.tar.gz"
sudo tar -xzf /tmp/hugo.tgz -C /usr/local/bin hugo
hugo version
```

- `run: |` — многострочный скрипт. По умолчанию выполняется в `bash -e`: первая упавшая команда
  останавливает шаг с ошибкой.
- `curl` флаги:
  - `-f` (`--fail`) — при HTTP-ошибке (404) завершиться с ошибкой. **Без `-f`** curl молча сохранит HTML-страницу
    «Not Found» в `hugo.tgz`, и упадёт уже `tar` с непонятным «not in gzip format»;
  - `-s` — не показывать индикатор загрузки (он засоряет лог), `-S` — но ошибки показывать;
  - `-L` — следовать редиректам. Ссылки на файлы релизов GitHub отвечают редиректом на хранилище файлов;
    **без `-L`** скачается пустой ответ-редирект;
  - `-o /tmp/hugo.tgz` — куда сохранить.
- `hugo_extended_…` — версия **extended** (глава 1: без неё нет WebP). Перепутать легко: рядом лежит
  `hugo_…` без `extended`, и сборка упадёт на первой же картинке.
- `tar -xzf архив -C /usr/local/bin hugo` — `-x` распаковать, `-z` через gzip, `-f` из файла, `-C` в папку,
  последний аргумент `hugo` — распаковать только этот файл (в архиве ещё README и LICENSE).
  `sudo` — потому что `/usr/local/bin` принадлежит root. Эта папка уже есть в `PATH`, так что дальше просто `hugo`.
- `hugo version` — печатает версию в лог. Через полгода по логу видно, чем собиралась конкретная версия сайта.

**А если иначе:**
- готовое действие `peaceiris/actions-hugo` делает то же одной строкой `uses:` — но это ещё одна чужая зависимость;
- `sudo apt-get install hugo` — в репозиториях Ubuntu Hugo обычно сильно устаревший и не всегда extended;
- `sudo snap install hugo` — свежий, но версию не зафиксировать так просто.

#### Сборка

```yaml
      - name: Собрать сайт
        env:
          SITE_URL: ${{ vars.SITE_URL }}
        run: |
          if [ -n "$SITE_URL" ]; then
            hugo --gc --minify --baseURL "${SITE_URL%/}/"
          else
            echo "::warning::Переменная SITE_URL не задана — ссылки будут на localhost. См. README → Деплой."
            hugo --gc --minify
          fi
```

- **`vars.SITE_URL`** — *переменная* репозитория (Settings → Secrets and variables → Actions → Variables).
  **Переменные** видны в логах и интерфейсе — для несекретного (адрес сайта). **Секреты** (`secrets.*`) GitHub
  маскирует в логах звёздочками и никому не показывает после сохранения — для ключей и паролей.
  Адрес сайта не секрет, а держать его в переменной удобнее: видно, что задано.
- **`env:` на уровне шага** — значение из `vars` попадает в переменную окружения, а скрипт читает её как `$SITE_URL`.
- **`hugo --baseURL`** — подменяет `baseURL: http://localhost:1313/` из `hugo.yaml` (глава 2).
  От него зависят абсолютные ссылки: `canonical`, Open Graph, RSS, `sitemap.xml` (глава 7).
- **`"${SITE_URL%/}/"`** — раскрытие параметра в bash: `%/` отрезает один `/` в конце, если он есть,
  затем `/` добавляется заново. Результат всегда с одним слэшем, как бы ни записали переменную.
  **Проверено:** и `https://example.com`, и `https://example.com/` дают `https://example.com/`.
  Похожие приёмы: `${X#prefix}` — отрезать начало, `${X%%.*}` — отрезать всё от первой точки, `${X:-default}` — значение по умолчанию.
- **`::warning::текст`** — команда для GitHub: строка превращается в жёлтое предупреждение на странице запуска.
  Есть ещё `::error::` и `::notice::`. Здесь вместо падения — предупреждение: свежий форк репозитория
  собирается без всякой настройки, а сообщение подсказывает, что делать.
- **`--gc --minify`** — то же, что `make build` (глава 2): убрать неиспользуемые кешированные ресурсы
  и минифицировать HTML/CSS/XML.

#### Артефакт

```yaml
      - uses: actions/upload-artifact@v7
        with:
          name: public
          path: public
          retention-days: 7
```

Задача `deploy` выполняется на **другой** машине, где папки `public/` нет. Артефакт — способ передать файлы
между задачами: `build` загружает `public/` в хранилище GitHub под именем `public`, `deploy` скачивает.

- `retention-days: 7` — через неделю артефакт удалится. По умолчанию — 90 дней; сборки копились бы
  и съедали квоту хранилища. Неделя — достаточно, чтобы скачать сборку PR и посмотреть её глазами.
- Артефакт PR можно скачать со страницы запуска (раздел Artifacts) — это готовый сайт, его можно открыть локально:
  `python3 -m http.server -d public`.

**А если иначе:** собрать и выложить в одной задаче — на одну машину и один артефакт меньше. Разделение даёт:
сборка проверяется на PR без всякого доступа к серверу, а секреты деплоя доступны только задаче `deploy`
в окружении `production`.

### Задача `deploy`

```yaml
  deploy:
    needs: build
    if: github.event_name != 'pull_request' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
```

- **`needs: build`** — стартовать только после успешного `build`. Если сборка упала, выкладывать нечего, и
  `deploy` будет пропущен — на сервере остаётся прошлая рабочая версия.
- **`if:`** — условие на выражениях GitHub. Две части:
  - `github.event_name != 'pull_request'` — не деплоить из PR;
  - `github.ref == 'refs/heads/main'` — и только из `main`. Нужно из-за `workflow_dispatch`: кнопку Run workflow
    можно нажать для любой ветки, и без этой проверки экспериментальная ветка оказалась бы на проде.
- **`environment: production`** — задача работает в *окружении*. Если его нет, GitHub создаст пустое.
  В Settings → Environments окружению можно задать:
  - **Required reviewers** — деплой ждёт, пока вы нажмёте «Approve»;
  - **Wait timer** — задержка перед деплоем;
  - **Deployment branches** — разрешить только `main`;
  - **свои секреты** — видимые только задачам этого окружения. Перенесите `DEPLOY_*` сюда, и задача `build`
    (в том числе в PR) физически не сможет их прочитать.

  Плюс история выкладок на главной странице репозитория (блок Deployments).

#### Шаги

```yaml
      - uses: actions/checkout@v7
        with:
          sparse-checkout: deploy
```

Нужен только `deploy/publish.sh`. `sparse-checkout: deploy` скачивает папку `deploy/` (и файлы из корня),
без `content/` со всеми картинками. На маленьком сайте выигрыш незаметен, на сайте с гигабайтом картинок — заметен.

```yaml
      - uses: actions/download-artifact@v8
        with:
          name: public
          path: public
```

Скачать артефакт `public` в папку `public/`. **Без `path`** файлы оказались бы прямо в рабочей папке,
вперемешку с `deploy/`.

#### Выкладка

```yaml
        env:
          DEPLOY_HOST: ${{ secrets.DEPLOY_HOST }}
          ...
        run: |
          if [ -z "$DEPLOY_HOST" ]; then
            echo "::warning::Секреты деплоя не заданы — сайт собран, но не выложен. См. README → Деплой."
            exit 0
          fi
```

- Секреты передаются через `env`, а не вставляются в скрипт как `${{ secrets.X }}`. Выражение `${{ }}` подставляется
  в **текст** скрипта до запуска: если в значении окажутся кавычки или `$(...)`, они станут частью команды.
  Через переменную окружения значение остаётся данными. Для своих секретов это скорее аккуратность, а для
  того, что приходит извне (заголовок PR, имя ветки), — обязательное правило против инъекций.
- **Проверка внутри скрипта.** Секреты нельзя использовать в `if:` задачи или шага, поэтому проверка «секреты заданы?»
  сделана в bash. `exit 0` — шаг считается успешным: пока сервер не настроен, каждый push не будет краснеть.

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
printf '%s\n' "$DEPLOY_SSH_KEY" > ~/.ssh/id_deploy && chmod 600 ~/.ssh/id_deploy
printf '%s\n' "$DEPLOY_KNOWN_HOSTS" > ~/.ssh/known_hosts
```

- **`chmod 700 ~/.ssh`, `chmod 600 id_deploy`** — SSH отказывается использовать ключ, который могут читать другие
  пользователи («UNPROTECTED PRIVATE KEY FILE!»).
- **`printf '%s\n'`, а не `echo`** — печатает значение ровно как есть и гарантирует перевод строки в конце.
  `echo` в некоторых оболочках обрабатывает `\n` и `-e` внутри строки, а без завершающего перевода строки
  OpenSSH может не прочитать ключ. При копировании ключа в секрет перевод строки в конце часто теряется — `printf` его возвращает.
  **Проверено:** `printf '%s\n'` добавляет `\n` после `-----END…-----`.
- **`known_hosts`** — отпечаток ключа *сервера* (из `ssh-keyscan`, глава 10). SSH сверяет его при подключении:
  если кто-то подменил сервер (перехватил DNS или IP), отпечаток не совпадёт и соединение оборвётся.

  **А если иначе:** `-o StrictHostKeyChecking=no` — так часто пишут в примерах, чтобы «не мешало».
  Тогда SSH примет любой сервер, и ваш деплой-ключ будет предъявлен кому угодно, кто ответит по этому адресу.
  Промежуточный вариант `StrictHostKeyChecking=accept-new` доверяет первому подключению — но в CI каждое подключение
  «первое», так что это то же самое `no`.

```bash
export RSYNC_RSH="ssh -i ~/.ssh/id_deploy -o IdentitiesOnly=yes"
bash deploy/publish.sh public "$DEPLOY_USER@$DEPLOY_HOST" "${GITHUB_SHA::12}"
```

- **`RSYNC_RSH`** — какой командой `rsync` подключается к серверу. `publish.sh` использует её же для своей
  SSH-команды (`RSH=${RSYNC_RSH:-ssh}`, глава 11), так что ключ указан в одном месте.
  - `-i ~/.ssh/id_deploy` — каким ключом входить;
  - `-o IdentitiesOnly=yes` — **только** этим ключом. Без опции SSH сначала перебирает другие ключи
    (из агента, стандартные `id_*`), и сервер после нескольких неудач обрывает соединение: «Too many authentication failures».
- **`${GITHUB_SHA::12}`** — первые 12 символов хеша коммита (подстрока в bash: `${X:начало:длина}`, начало пропущено).
  Это имя папки выпуска на сервере. **Проверено:** `4f3949548aa0f307e…` → `4f3949548aa0`.
  По имени выпуска сразу видно, какой коммит сейчас на сайте: `readlink /var/www/site/current`.

## Где ещё пригодится

**Кеш обработанных картинок.** Hugo кладёт уменьшенные картинки в `resources/_gen/`. На CI эта папка каждый раз пустая,
и все картинки обрабатываются заново. Когда картинок сотни, это минуты. Решение — шаг перед сборкой:

```yaml
      - uses: actions/cache@vN
        with:
          path: resources/_gen
          key: hugo-${{ env.HUGO_VERSION }}-${{ github.sha }}
          restore-keys: hugo-${{ env.HUGO_VERSION }}-
```

(`vN` — актуальная версия действия, см. его README.)

**Деплой на GitHub Pages** вместо своего сервера (глава 1). Задачу `deploy` заменяют на:

```yaml
permissions:
  pages: write
  id-token: write
# в build вместо upload-artifact:
      - uses: actions/upload-pages-artifact@vN
        with: { path: public }
# deploy:
    environment: github-pages
    steps:
      - uses: actions/deploy-pages@vN
```

Плюс в настройках репозитория: Pages → Source → GitHub Actions. Каталога `deploy/` и сервера тогда не нужно.

**Проверка ссылок.** После сборки шаг с [lychee](https://github.com/lycheeverse/lychee) или htmltest
проходит по `public/` и падает, если ссылка ведёт в никуда. Полезно на PR.

**Превью PR.** Сейчас превью — скачиваемый артефакт. Можно выкладывать сборку PR на поддомен
(`pr-12.preview.example.com`) тем же `publish.sh` в другую папку, а ссылку писать комментарием в PR.

**Обновление действий.** Файл `.github/dependabot.yml` с `package-ecosystem: github-actions` — Dependabot будет
сам присылать PR при выходе новых версий `actions/checkout` и других.

## Упражнения

1. В форке репозитория (без секретов) запустите workflow кнопкой Run workflow. Найдите оба предупреждения `::warning::`
   и скачайте артефакт. Откройте сайт из артефакта локально.
2. Добавьте `paths-ignore: ['docs/**']` к событию `push`. Проверьте, что правка учебника не запускает сборку,
   а правка записи — запускает.
3. Создайте окружение `production` с Required reviewers и посмотрите, как деплой ждёт одобрения.
4. Перенесите проверку «есть ли секреты» в отдельный шаг, который пишет результат в `$GITHUB_OUTPUT`,
   и сделайте шаг выкладки условным по `if: steps.<id>.outputs.<имя> == 'true'`.

## Итог

Workflow собирает сайт на каждый push и PR, а выкладывает только из `main`. Версия Hugo зафиксирована в `env`,
адрес сайта — в переменной, доступ к серверу — в секретах. Собранный `public/` передаётся между задачами артефактом,
деплои не пересекаются благодаря `concurrency`. Ключ SSH записывается с правильными правами,
сервер проверяется по `known_hosts`, а имя выпуска — короткий хеш коммита.
