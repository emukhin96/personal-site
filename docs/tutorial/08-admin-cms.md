# Глава 8. Админка на Sveltia CMS

## Зачем

Владелец сайта должен писать записи и менять «Обо мне» из браузера, в том числе с телефона,
не открывая редактор кода и не набирая `git push`. При этом тексты должны остаться Markdown-файлами
в репозитории: с историей, откатом и без отдельной базы данных.

Это делает **git-CMS**: веб-страница, которая показывает формы, а при сохранении сама делает
коммит в репозиторий. Здесь используется [Sveltia CMS](https://sveltiacms.app) — современная замена
Decap CMS (бывшей Netlify CMS) с тем же форматом конфига.

## Как устроена git-CMS

```
Браузер владельца                         GitHub
┌──────────────────────────┐   HTTPS   ┌──────────────────────┐
│ /admin/index.html        │──────────▶│ GitHub API           │
│  └ sveltia-cms.js (SPA)  │◀──────────│  читает файлы,       │
│  └ /admin/config.yml     │           │  делает коммиты      │
└──────────────────────────┘           └──────────┬───────────┘
                                                  │ push в main
                                                  ▼
                                        GitHub Actions → сайт (глава 9)
```

Важные следствия:

- **На сервере нет ничего особенного.** `/admin/` — два статических файла, Caddy отдаёт их как любые другие.
  Вся логика выполняется в браузере владельца. Сервер не знает ни о каких пользователях.
- **Права проверяет GitHub.** Админку может открыть кто угодно, но без токена с правом записи
  в репозиторий она ничего не прочитает (если репозиторий приватный) и ничего не запишет.
- **Каждое сохранение — коммит в `main`.** Он запускает сборку, через минуту правка на сайте.
  Отменить правку можно обычным `git revert`.
- **CMS знает о структуре файлов только из `config.yml`.** Шаблоны Hugo она не читает. Поэтому
  поля в админке и поля, которые ждут шаблоны, нужно держать согласованными вручную (раздел «Правило синхронизации»).

## Как сделано здесь: `static/admin/index.html`

Всё, что лежит в `static/`, Hugo копирует на сайт без изменений (глава 2), поэтому
`static/admin/index.html` становится страницей `https://<домен>/admin/`.

```html
<!doctype html>
<html lang="ru">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <meta name="robots" content="noindex">
  <title>Админка</title>
</head>
<body>
  <!-- Версия зафиксирована; обновление — сменить номер и проверить админку. -->
  <script src="https://unpkg.com/@sveltia/cms@0.255.1/dist/sveltia-cms.js"></script>
</body>
</html>
```

### Разбор

- **`<meta name="robots" content="noindex">`** — просит поисковики не показывать страницу входа в выдаче.
  То же самое Caddy дублирует заголовком `X-Robots-Tag noindex` для всего `/admin/*` (глава 10):
  заголовок действует и на `config.yml`, у которого нет `<head>`.
- **`<script src="https://unpkg.com/@sveltia/cms@0.255.1/...">`** — весь код админки. unpkg — CDN,
  который раздаёт файлы npm-пакетов. Скрипт сам находит `config.yml` рядом со страницей
  (по умолчанию ищет `./config.yml`) и рисует интерфейс прямо в `<body>`.
- **`<body>` пустой** — так и задумано: Sveltia строит интерфейс сама.

### А если иначе

| Вариант | Что будет |
|---|---|
| `@sveltia/cms/dist/sveltia-cms.js` (без версии) | unpkg отдаст последнюю версию. Админка может измениться или сломаться в любой день без единого коммита в репозитории. Поэтому версия зафиксирована |
| `@sveltia/cms@0/dist/...` | Последняя версия с мажорной цифрой 0. Для пакета версии `0.x` это почти то же, что «последняя»: по semver в `0.x` ломающие изменения допустимы в любом минорном выпуске |
| Скачать файл в `static/admin/` | Админка не зависит от unpkg. Минус — ~1,5 МБ JS в репозитории, обновлять вручную |
| Добавить `integrity="sha384-…" crossorigin="anonymous"` | Браузер проверит хеш скрипта и откажется выполнять его, если файл на CDN подменили. Хеш считается так: `curl -fsSL <URL> \| openssl dgst -sha384 -binary \| openssl base64 -A`. При обновлении версии хеш нужно пересчитать |
| Убрать `noindex` и заголовок в Caddy | Страница входа может попасть в поиск. Это не дыра (без токена ничего не сделать), но лишнее |

Обновление: поменять номер версии в URL, открыть `/admin/` локально (`make dev`) и проверить,
что записи открываются и сохраняются. Описание изменений — в [выпусках Sveltia CMS](https://github.com/sveltia/sveltia-cms/releases).

## Как сделано здесь: `static/admin/config.yml`

Это главный файл главы. Разберём его по частям.

### Подключение к репозиторию: `backend`

```yaml
backend:
  name: github
  repo: emukhin96/personal-site
  branch: main
  # Вход по личному токену GitHub — не нужен отдельный OAuth-сервер.
  auth_methods: [token]
  commit_messages:
    create: 'Админка: создано «{{slug}}» в «{{collection}}»'
    update: 'Админка: обновлено «{{slug}}» в «{{collection}}»'
    delete: 'Админка: удалено «{{slug}}» из «{{collection}}»'
    uploadMedia: 'Админка: загружен файл {{path}}'
    deleteMedia: 'Админка: удалён файл {{path}}'
```

- **`name: github`** — с каким хостингом git работать. Ещё бывают `gitlab`, `gitea`, `forgejo` и `test-repo`
  (данные только в памяти браузера — для экспериментов с конфигом). Для другого хостинга меняется
  только этот блок; коллекции остаются прежними.
- **`repo: владелец/репозиторий`** — куда коммитить. Если сделать форк проекта, это первое, что нужно поменять,
  иначе админка будет стучаться в чужой репозиторий и получит отказ.
- **`branch: main`** — ветка для коммитов. Без этой строки Sveltia возьмёт ветку по умолчанию репозитория.
  Её указывают явно, чтобы не зависеть от настроек GitHub, и потому что деплой (глава 9) срабатывает
  именно на `main`. Если поставить `branch: drafts`, правки будут копиться в отдельной ветке
  и не попадут на сайт, пока вы не сольёте её в `main` — простой способ сделать «черновой» режим.
- **`auth_methods: [token]`** — как входить. Варианты:
  - `token` — пользователь вставляет личный токен GitHub (подробности ниже). Ничего дополнительно разворачивать не нужно;
  - `oauth` — кнопка «Войти через GitHub». Для неё нужен OAuth-посредник: GitHub требует секрет приложения,
    а его нельзя хранить в браузере. Обычно поднимают [sveltia-cms-auth](https://github.com/sveltia/sveltia-cms-auth)
    на Cloudflare Workers (бесплатно) и указывают его адрес в `base_url`. Если сайт на Netlify, посредником
    может быть сам Netlify (так работала Netlify CMS);
  - без этой строки разрешены оба способа, но `oauth` без посредника работать не будет —
    пользователь увидит кнопку, которая ведёт в никуда. Пустой список `[]` — ошибка конфига.

  **Проверено:** опечатка `auth_methods: [tokn]` ловится JSON-схемой: «must be equal to one of the allowed values».
- **`commit_messages`** — шаблоны сообщений коммитов. Плейсхолдеры: `{{slug}}` — адрес записи, `{{collection}}` —
  название коллекции, `{{path}}` — путь загруженного файла. Есть и `{{author-login}}`, `{{author-name}}`,
  `{{author-email}}` — пригодятся, если в админке работают несколько человек. Без блока сообщения будут
  английскими («Create posts “…”»). Русские сообщения удобны: в истории git сразу видно, какие коммиты
  сделала админка, а какие — человек.

**Где ещё пригодится:** опция `skip_ci: true` в `backend` добавляет `[skip ci]` к сообщениям, и GitHub Actions
не запускается на каждую правку; в интерфейсе появляется кнопка ручного запуска деплоя. Полезно, если
вы делаете много мелких правок подряд и не хотите десяти сборок.

### Общие настройки

```yaml
app_title: Админка сайта

# Общая медиатека (аватар и картинки, которые нужны в разных местах).
# Картинки записей и проектов лежат рядом с ними, в папке записи.
media_folder: assets/uploads
public_folder: /uploads

slug:
  encoding: ascii
  clean_accents: true
  timezone: local

output:
  omit_empty_optional_fields: true
```

- **`app_title`** — заголовок вкладки и экрана входа. По умолчанию «Sveltia CMS».
- **`media_folder: assets/uploads`** — куда в репозитории класть загруженные файлы, если у коллекции
  не задано своё место. Путь от корня репозитория.
- **`public_folder: /uploads`** — что записать в поле, когда файл выбран. Файл лежит в `assets/uploads/photo.jpg`,
  а в `data/site.yaml` запишется `avatar: /uploads/photo.jpg`.

  Почему `assets/`, а не `static/`: файлы из `static/` Hugo только копирует, а из `assets/` умеет обрабатывать —
  уменьшать, обрезать, переводить в WebP (глава 5). Путь `/uploads/photo.jpg` превращается в ресурс в
  `layouts/_partials/resolve-image.html`:

  ```go-html-template
  {{- if not $res }}{{ $res = resources.Get (strings.TrimPrefix "/" $path) }}{{ end }}
  ```

  `resources.Get` ищет внутри `assets/`, поэтому `/uploads/photo.jpg` → `assets/uploads/photo.jpg`.
  **А если иначе:** `media_folder: static/uploads` — картинки появятся на сайте как есть, без уменьшения;
  `resolve-image.html` их не найдёт, и аватар на главной не выведется (шаблон `home.html` выводит его только
  как обработанный ресурс).
- **`slug`** — как из заголовка получается адрес страницы (slug):
  - `encoding: ascii` — в адресе только латиница, цифры и дефисы. По умолчанию `unicode`: адрес остался бы
    кириллическим, `/posts/как-начинался-проект/`. Такие адреса работают, но в ссылках превращаются
    в `%D0%BA%D0%B0%D0%BA-...`, и их неудобно пересылать;
  - `clean_accents: true` — перед очисткой транслитерировать: «Как начинался проект» → `kak-nachinalsya-proekt`.
    По исходному коду Sveltia без этой опции при `encoding: ascii` все не-ASCII символы заменяются дефисом,
    и из русского заголовка адреса почти не останется. Поэтому эти две опции идут парой;
  - `timezone: local` — часовой пояс для шаблонов адреса с датой (`{{year}}`, `{{month}}`, `{{day}}`).
    Здесь адрес строится только из заголовка, так что опция на будущее. По умолчанию `utc`: запись,
    созданная в 01:00 по Москве, получила бы в адресе вчерашнюю дату.
- **`output.omit_empty_optional_fields: true`** — не записывать в файл пустые необязательные поля.
  Без этой опции во front matter появлялись бы строки `cover: ''`, `summary: ''`. Шаблонам это не мешает
  (`with` пропускает пустую строку, глава 4), но файлы становятся шумными, и в diff каждого коммита
  лишние строки.

### Коллекция «Проекты»

```yaml
collections:
  - name: projects
    label: Проекты
    label_singular: проект
    icon: deployed_code
    folder: content/projects
    path: '{{slug}}/index'
    media_folder: ''
    public_folder: ''
    slug:
      template: '{{title}}'
      editable: [create]
      hint: Адрес страницы — /projects/адрес/. Его используют записи, поэтому после создания он не меняется.
      pattern: ['^[a-z0-9]+(-[a-z0-9]+)*$', 'Только латиница в нижнем регистре, цифры и дефисы']
    reorder:
      key: weight
    summary: '{{title}}'
    preview_path: /projects/{{slug}}/
```

**Коллекция** — набор однотипных записей. Бывают два вида: *папка* (`folder`) — каждый файл в папке
это запись, их можно создавать и удалять; и *файлы* (`files`) — фиксированный список конкретных файлов.
Здесь «Проекты» и «Записи» — папки, а настройки сайта — синглтон (см. ниже).

- **`name`** — внутреннее имя, участвует в URL админки и в `{{collection}}` сообщений коммитов.
  `label` / `label_singular` — подписи в интерфейсе («Новый проект»).
- **`icon`** — имя иконки из набора [Material Symbols](https://fonts.google.com/icons).
- **`folder: content/projects`** — где лежат записи. Совпадает с разделом Hugo (глава 3).
- **`path: '{{slug}}/index'`** — путь файла внутри `folder`, без расширения. Новый проект «Мой бот»
  станет `content/projects/moi-bot/index.md`. Это и есть **бандл страницы** Hugo (глава 3): папка, в которой
  `index.md` и картинки лежат вместе.

  **А если иначе:** без `path` файл был бы `content/projects/moi-bot.md`. Hugo сделал бы из него такую же
  страницу, но картинки положить «рядом» уже нельзя: у страницы нет своей папки, и `.Resources.Get "cover.jpg"`
  ничего не найдёт.
- **`media_folder: ''` и `public_folder: ''`** — картинки, загруженные в поля этого проекта, кладутся
  в папку самой записи, а в поле пишется только имя файла: `cover: cover.jpg`. В `resolve-image.html` такой путь
  (без `/` в начале) ищется первым — среди ресурсов страницы:

  ```go-html-template
  {{- with $.page }}{{ $res = .Resources.Get $path }}{{ end }}
  ```

  Для коллекции с `path` Sveltia и по умолчанию кладёт медиа в папку записи; пустые строки записаны явно,
  чтобы это было видно из конфига и не зависело от умолчаний. **А если убрать и заменить на `media_folder: /assets/uploads`:**
  все картинки всех записей окажутся в одной куче, при удалении записи её картинки останутся сиротами,
  а пути станут `/uploads/...`.
- **`slug.template: '{{title}}'`** — адрес по умолчанию строится из поля `title`. Можно, например, `'{{year}}-{{title}}'` —
  тогда адрес начнётся с года.
- **`slug.editable: [create]`** — адрес можно поправить только при создании, потом поле адреса заблокировано.
  Варианты: `true` (всегда), `false` (никогда, только из шаблона), `[update]`.

  **Почему нельзя менять адрес проекта потом.** Записи ссылаются на проект именно по адресу (имени папки):
  `projects: [primer-proekta]`. Если переименовать папку, все такие ссылки перестанут находить проект —
  записи пропадут из его хронологии без единой ошибки при сборке (`site.GetPage` просто вернёт пустоту,
  глава 4). Плюс сломаются внешние ссылки на `/projects/старый-адрес/`.
- **`slug.hint`** — подсказка под полем.
- **`slug.pattern`** — регулярное выражение и текст ошибки. `^[a-z0-9]+(-[a-z0-9]+)*$` — одно или несколько
  «слов» из строчных латинских букв и цифр, разделённых одиночными дефисами: `moi-bot-2` подходит,
  `Moi_Bot`, `-bot`, `bot--2` — нет. Страхует, если владелец решит ввести адрес вручную.
- **`reorder.key: weight`** — в списке проектов появляется перетаскивание, порядок сохраняется числом
  в поле `weight` (1, 2, 3…). Hugo сортирует по тому же полю: в `home.html` и `projects/section.html` стоит
  `.Pages.ByWeight`. **А если иначе:** без `key` Sveltia записала бы поле `order`, которого Hugo не знает, —
  перетаскивание в админке ни на что бы не влияло. Без `reorder` порядок можно задать только руками в файлах.
- **`summary: '{{title}}'`** — как запись выглядит в списке админки. Можно `'{{title}} — {{status}}'`.
- **`preview_path: /projects/{{slug}}/`** — по нему админка строит ссылку «открыть на сайте». Должен совпадать
  с `permalinks` в `hugo.yaml` (глава 2), иначе ссылка будет вести на 404.

### Поля проекта и виджеты

```yaml
    fields:
      - { name: title, label: Название, widget: string }
      - name: summary
        label: Кратко
        widget: text
        hint: Одна-две строки для списка проектов.
      - name: status
        label: Статус
        widget: select
        default: active
        options:
          - { label: В работе, value: active }
          - { label: На паузе, value: paused }
          - { label: Завершён, value: finished }
          - { label: В архиве, value: archived }
      - { name: started, label: Дата начала, widget: datetime, type: date, required: false }
      - name: links
        label: Ссылки
        label_singular: ссылку
        widget: list
        required: false
        summary: '{{label}} — {{url}}'
        fields:
          - { name: label, label: Подпись, widget: string }
          - { name: url, label: Адрес, widget: string }
      - { name: cover, label: Обложка, widget: image, required: false }
      - { name: body, label: Описание, widget: markdown, required: false }
```

Каждое поле — это ключ во front matter (`name`) и способ его редактировать (`widget`).
`{ name: …, label: … }` и многострочная запись — один и тот же YAML, просто два стиля.

| Виджет | Что в файле | Параметры здесь | Другие полезные параметры |
|---|---|---|---|
| `string` | одна строка | — | `pattern`, `default` |
| `text` | многострочный текст без форматирования | `hint` | `minimal` |
| `select` | одно из значений `options` | `default: active` | `multiple: true` — список; `dropdown_threshold` — до скольких вариантов показывать радиокнопки вместо выпадающего списка (по умолчанию 5) |
| `datetime` | дата | `type: date` — только дата, без времени | `format` (токены Day.js), `default: '{{now}}'`, `min`, `max` |
| `list` | список объектов | `fields` — поля элемента, `summary` — подпись свёрнутого элемента | `min`, `max`, `collapsed`, `field` (одно поле — список строк) |
| `image` | путь к файлу | — | `accept`, `multiple`, `media_folder` на уровне поля |
| `markdown` | текст после front matter (для `name: body`) | — | `buttons`, `modes: [raw, rich_text]`, `minimal` |
| `boolean` | `true` / `false` | — | `default` |
| `relation` | адрес(а) записей другой коллекции | см. ниже | `search_fields`, `min`, `max` |
| `color` | `#rrggbb` | `allowInput: true` — поле для ручного ввода | `enableAlpha` |

Связь со шаблонами:

- **`status`**: в файл пишется `value` (`active`), а не `label` («В работе»). Шаблон `_partials/status.html`
  переводит значение обратно в текст:

  ```go-html-template
  {{- $labels := dict "active" "в работе" "paused" "на паузе" "finished" "завершён" "archived" "в архиве" }}
  ```

  Хранить машинное значение правильно: можно переименовать подпись, не трогая файлы, и стилизовать
  `.status-active` в CSS. **Если добавить новый статус** только в `config.yml`, шаблон выведет его как есть
  (`index $labels . | default .`), то есть латиницей. Новый статус надо добавлять в оба места.
- **`started`** с `type: date` пишется как `2026-01-15`. Без `type: date` виджет запросил бы и время,
  и в файле было бы `2026-01-15T10:00:00+03:00`. Hugo понимает оба формата, но время проекту не нужно.
- **`body`** — особое имя: содержимое не попадает во front matter, а становится текстом файла после `---`.
  Это то, что шаблон выводит через `.Content`.

### Коллекция «Записи» и связь с проектами

Начало совпадает с проектами (папка, бандлы, slug). Отличия:

```yaml
    summary: '{{title}} — {{date | date("DD.MM.YYYY")}}'
    sortable_fields:
      fields: [date, title]
      default: { field: date, direction: descending }
```

- **`summary`** с фильтром: `{{date | date("DD.MM.YYYY")}}` форматирует дату в списке. Есть и другие фильтры —
  `upper`, `lower`, `truncate(50)`, `default('—')`.
- **`sortable_fields`** — по каким полям можно сортировать список в админке и как он отсортирован
  при открытии: новые записи сверху. Без `default` список открывался бы по алфавиту.
- Нет `reorder`: порядок записей определяет дата, а не перетаскивание.

```yaml
    fields:
      - { name: title, label: Заголовок, widget: string }
      - { name: date, label: Дата, widget: datetime, type: date, default: '{{now}}' }
      - name: projects
        label: Проект
        widget: relation
        collection: projects
        value_field: '{{slug}}'
        display_fields: [title]
        multiple: true
        required: false
        hint: Запись появится в хронологии выбранных проектов.
      - name: summary
        label: Кратко
        widget: text
        required: false
        hint: Подзаголовок в списках записей.
      - { name: cover, label: Обложка, widget: image, required: false }
      - { name: draft, label: Черновик, widget: boolean, default: false, required: false, hint: Черновики не публикуются на сайте. }
      - { name: body, label: Текст, widget: markdown }
```

- **`date`** с `default: '{{now}}'` — новая запись получает сегодняшнюю дату. Помните о `buildFuture` (глава 3):
  если поставить дату в будущем, Hugo не опубликует запись, пока эта дата не наступит и сайт не пересоберётся.
- **`projects` — виджет `relation`**, ключ всей модели «запись → проекты»:
  - `collection: projects` — из какой коллекции выбирать;
  - `value_field: '{{slug}}'` — что записать в файл: адрес проекта, то есть имя его папки.
    В фигурных скобках — именно адрес записи; `slug` без скобок означал бы поле с именем `slug`;
  - `display_fields: [title]` — что показать в выпадающем списке: названия, а не адреса;
  - `multiple: true` — можно выбрать несколько проектов, в файл запишется список:

    ```yaml
    projects:
      - primer-proekta
    ```

  В Hugo этот список читает `_partials/project-posts.html`:

  ```go-html-template
  {{- $slug := .File.ContentBaseName }}
  {{- $posts := where (where site.RegularPages "Section" "posts") "Params.projects" "intersect" (slice $slug) }}
  ```

  `.File.ContentBaseName` у бандла — имя папки, то есть то же самое, что записала админка в `value_field: '{{slug}}'`.
  Обе стороны говорят на одном языке — имени папки проекта.

  **А если иначе:**
  - `value_field: title` — в файл запишутся названия («Пример проекта»). Шаблон сравнивает с именем папки
    и ничего не найдёт: хронологии опустеют. Пришлось бы менять шаблон, а переименование проекта ломало бы связи;
  - `multiple: false` — в файл запишется строка `projects: primer-proekta`, а не список. `intersect` в `where`
    ждёт список, и связь сломается. Если нужен ровно один проект, лучше оставить `multiple: true` и добавить `max: 1`;
  - без `required: false` нельзя сохранить запись, не относящуюся ни к одному проекту.
- **`draft`** — Hugo не публикует страницы с `draft: true` (кроме `make dev`, где включён `--buildDrafts`).
  Это «черновик» без отдельного механизма: файл уже в репозитории, но на сайте его нет.

### Синглтон «Настройки сайта»

```yaml
singletons:
  - name: settings
    label: Настройки сайта
    icon: settings
    file: data/site.yaml
    fields:
      - { name: name, label: Имя, widget: string, hint: Заголовок главной и название сайта. }
      ...
      - { name: accent, label: Цвет акцента, widget: color, allowInput: true, default: '#2563eb' }
```

**Синглтон** — один файл, а не коллекция. В меню админки он виден сразу, без списка записей.
Здесь это `data/site.yaml`: имя, подзаголовок, «обо мне», фото, ссылки, подвал, цвет акцента.
Hugo читает его как `hugo.Data.site` (главы 3 и 4).

- Формат определяется по расширению: `.yaml` → чистый YAML без front matter, поэтому поле `about` с виджетом
  `markdown` — это просто многострочная строка (`about: |-`), а не текст после `---`. В шаблоне она проходит через
  `markdownify`.
- **`avatar`** — виджет `image` без своих `media_folder`/`public_folder`, значит, используются глобальные:
  файл в `assets/uploads/`, в YAML — `/uploads/имя.jpg`. Ровно то, что ждёт `resolve-image.html`.
- **`accent`** — виджет `color` пишет `#rrggbb`. В `head.html` он попадает в CSS-переменную
  `--accent` (глава 6). С `enableAlpha: true` можно было бы сохранить и прозрачность (`#rrggbbaa`) — CSS это понимает.

**А если иначе:** то же можно описать старым способом — коллекцией `files` с одним файлом.
Синглтоны удобнее: не нужно заходить в коллекцию, чтобы увидеть единственный пункт.

## Правило синхронизации

Админка и шаблоны не знают друг о друге. Из `AGENTS.md`:

> Любое изменение полей во front matter или в `data/site.yaml` делать **одновременно** в шаблонах
> и в конфиге админки; конфиг проверять по схеме `@sveltia/cms/schema/sveltia-cms.json`.

Пример: вы хотите у записей поле «Время чтения».

1. В `config.yml` у коллекции `posts`: `- { name: reading, label: Минут на чтение, widget: number, required: false }`.
2. В `layouts/posts/page.html`: `{{ with .Params.reading }}<span>{{ . }} мин</span>{{ end }}`.
3. Проверить конфиг по схеме (ниже) и собрать сайт `hugo --gc --minify`.

Если сделать только шаг 1 — поле будет сохраняться, но нигде не появится. Только шаг 2 — поле придётся
вписывать руками в файл, админка его не покажет.

### Проверка конфига по JSON-схеме

В npm-пакете `@sveltia/cms` лежит схема `schema/sveltia-cms.json`. Проверить конфиг можно так
(в отдельной папке, чтобы не засорять репозиторий):

```bash
npm install @sveltia/cms@0.255.1 ajv@8 ajv-formats@3 js-yaml@4
```

```js
// check.cjs: node check.cjs путь/к/config.yml
const Ajv = require('ajv'), addFormats = require('ajv-formats'), yaml = require('js-yaml'), fs = require('fs');
const schema = JSON.parse(fs.readFileSync('node_modules/@sveltia/cms/schema/sveltia-cms.json'));
const ajv = new Ajv({ strict: false, allErrors: true }); addFormats(ajv);
const validate = ajv.compile(schema);
const cfg = yaml.load(fs.readFileSync(process.argv[2], 'utf8'));
console.log(validate(cfg) ? 'OK' : validate.errors);
```

**Проверено:** текущий `config.yml` проходит схему без ошибок. Схема ловит неизвестные параметры
(`folde:` вместо `folder:` → «must NOT have additional properties»), неверные значения
(`auth_methods: [tokn]`, `name: gitea2`) и неверные типы (`multiple: "да"`). Но **опечатку в имени виджета**
(`widget: relaton`) схема не ловит — имена виджетов в ней не перечислены, потому что можно регистрировать свои.
Такую ошибку увидите только в самой админке.

Удобно и в редакторе: VS Code с расширением YAML подсказывает поля, если первой строкой `config.yml` написать
`# yaml-language-server: $schema=https://unpkg.com/@sveltia/cms@0.255.1/schema/sveltia-cms.json`.

## Вход по токену

Инструкция по созданию — в `README.md` (раздел «Админка»). Здесь — зачем каждый шаг.

- **Fine-grained token**, а не classic. Классический токен с правом `repo` даёт запись во **все** ваши
  репозитории. Fine-grained ограничивается одним репозиторием и конкретными правами.
- **Contents: Read and write** — читать и коммитить файлы. Больше админке ничего не нужно.
  **Metadata: Read-only** GitHub добавляет сам — без него токен не видит даже сам репозиторий.
- **Срок действия** задаётся при создании. Когда он истечёт, админка перестанет пускать —
  создайте новый токен и войдите снова. Короткий срок — меньше вреда, если токен утечёт.
- **Где хранится.** Только в браузере, где вы вошли: Sveltia кладёт данные входа в хранилище браузера
  под ключом `sveltia-cms.user` (видно в исходном коде пакета). На сервер сайта токен не попадает никогда.
  «Выйти» в админке стирает его.
- **Риски.** Кто получил токен, может переписать сайт (но не другие ваши репозитории и не настройки репозитория).
  Не входите в админку на чужих компьютерах; при подозрении на утечку — отзовите токен в настройках GitHub.
  Сайт сам не выполняет JavaScript (глава 1), поэтому украсть токен через страницу сайта на том же домене нечем —
  ещё одна причина не подключать к сайту сторонние скрипты.

## Локальная работа без токена

```bash
make dev
```

Откройте `http://localhost:1313/admin/` в Chrome или Edge → «Работать с локальным репозиторием» → выберите папку
репозитория. Sveltia использует **File System Access API** браузера (`showDirectoryPicker`): читает и пишет файлы
прямо на диске. `hugo server` видит изменения и сразу перезагружает страницу. Коммит делаете сами.

Работает только на `localhost` и только в браузерах с этим API (Chrome, Edge; в Firefox и Safari — нет).
Отдельный прокси-сервер, как у Decap CMS (`npx decap-server`), не нужен.

Это лучший способ отлаживать изменения в `config.yml`: никаких коммитов, видно, что именно админка пишет в файл.

## Где ещё пригодится

- Тот же `config.yml` с другими коллекциями подходит для документации, портфолио, сайта мероприятия —
  для любого генератора, который читает Markdown/YAML (Hugo, Eleventy, Astro, Jekyll).
- `publish_mode: editorial_workflow` — правки создаются как pull request'ы со статусами «черновик → на проверке → готово».
  Удобно, если пишут несколько человек и нужна вычитка.
- `i18n` — многоязычный контент: одна запись, несколько языковых версий.
- Виджет `relation` связывает что угодно: автора с постом, книгу с серией, доклад со спикером.

## Упражнения

1. Добавьте проекту поле «Технологии» (`widget: list`, `field: { name: tech, widget: string }` — список строк)
   и выведите его на странице проекта. Проверьте конфиг по схеме.
2. Поменяйте `encoding: ascii` на `unicode`, создайте в локальной админке запись с русским заголовком.
   Какой адрес получился? Откройте его в браузере и скопируйте ссылку в мессенджер — как она выглядит?
3. Поставьте `multiple: false` у поля `projects`, сохраните запись и посмотрите, что изменилось в файле
   и в хронологии проекта. Верните как было.
4. Сделайте `branch: drafts` и подумайте, как тогда публиковать правки. Какие шаги в главе 9 пришлось бы поменять?

## Итог

Админка — статическая страница со скриптом Sveltia CMS и конфигом `config.yml`. Конфиг описывает,
где лежат файлы (коллекции и синглтон) и какие в них поля (виджеты). Сохранение — коммит через GitHub API
по токену, который хранится только в браузере. Ключевые связки с Hugo: `path: '{{slug}}/index'` — бандлы,
`media_folder: ''` — картинки рядом с записью, `relation` с `value_field: '{{slug}}'` — список имён папок
проектов, `reorder.key: weight` — порядок проектов. Меняете поле в одном месте — меняйте и в другом.
