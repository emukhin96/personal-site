# Глава 2. Hugo: установка, папки, настройки

## Зачем

Hugo — программа, которая берёт тексты из `content/`, шаблоны из `layouts/`, стили и картинки из `assets/`
и собирает из них папку `public/` с готовым сайтом. В этой главе вы установите Hugo, разберётесь,
что в какой папке лежит и почему, и пройдёте по каждой строке файла настроек `hugo.yaml`.

## Как сделано здесь

- Версия Hugo: **0.169.0 extended**. Она записана в одном месте — в `.github/workflows/deploy.yml`:

  ```yaml
  env:
    HUGO_VERSION: 0.169.0
  ```

- Настройки сайта: `hugo.yaml` в корне.
- Команды для разработки: `Makefile` (`make dev`, `make build`, `make clean`).
- Что не попадает в git: `.gitignore`.

## Установка

### Какая версия и почему именно она

Hugo часто выходит, и между версиями меняются названия функций и правила поиска шаблонов.
Например, в 0.146 появилась новая структура `layouts/` (`home.html`, `_partials/`), а в 0.156
`.Site.Data` объявили устаревшим в пользу `hugo.Data`. Шаблоны этого проекта написаны под 0.169.

Поэтому правило одно: **локально ставьте ту же версию, что в CI.** Иначе возможны две неприятности:

- локально всё работает, а в CI сборка падает (в CI версия старее, и там нет функции, которую вы использовали);
- в CI всё собирается, а у вас локально сыплются предупреждения о «deprecated» (у вас версия новее).

Ставьте сборку **extended** — ту же, что в CI. Исторически только в ней был кодировщик WebP (глава 5) и компилятор SCSS,
и многие инструкции до сих пор говорят «нужна extended». **Проверено:** обычная (не extended) сборка Hugo 0.169
собирает этот проект без ошибок и тоже создаёт `chart_hu_….webp` — в новых версиях WebP есть в обеих.
Но для одинакового результата локально и в CI берите одну и ту же сборку.

### Способы установки

**1. Готовый исполняемый файл** (работает везде, точная версия):

```bash
# Linux x86-64. Для Mac на той же странице релиза — hugo_extended_0.169.0_darwin-universal.pkg,
# для Windows — hugo_extended_0.169.0_windows-amd64.zip
curl -fsSL -o hugo.tgz \
  https://github.com/gohugoio/hugo/releases/download/v0.169.0/hugo_extended_0.169.0_linux-amd64.tar.gz
tar -xzf hugo.tgz hugo
sudo mv hugo /usr/local/bin/
```

Так же Hugo ставится в CI (глава 9). Файл один, ничего больше не нужно: ни Go, ни Node.js.

**2. Пакетный менеджер** (удобно, но версия — какая есть в репозитории пакетов):

```bash
brew install hugo                     # macOS: сразу extended, последняя версия
winget install Hugo.Hugo.Extended     # Windows
sudo snap install hugo                # Linux: snap, extended
```

Пакеты в `apt` у Debian/Ubuntu часто сильно отстают — для этого проекта они не годятся.

**3. Через Go** (`go install -tags extended github.com/gohugoio/hugo@v0.169.0`) — нужен компилятор Go и C,
обычно незачем.

### Проверка

```bash
hugo version
# hugo v0.169.0-1da10fc44701c566b1669cdb2d12638f155138bd+extended linux/amd64 BuildDate=2026-10-27T14:52:20Z VendorInfo=gohugoio
```

Смотрите на две вещи: номер версии и слово `+extended` (у обычной сборки его нет).

## Структура проекта

Новый пустой проект создаёт команда `hugo new project <папка>` (в старых версиях — `hugo new site`, она тоже работает).
**Проверено:** она создаёт `archetypes/`, `assets/`, `content/`, `data/`, `i18n/`, `layouts/`, `static/`, `themes/` и `hugo.toml`.
В этом проекте `archetypes/` и `themes/` не нужны (темы нет, записи создаются через админку),
а настройки записаны в YAML (`hugo.yaml`) — так их проще читать рядом с YAML-конфигом админки.

| Папка | Что в ней | Как Hugo с ней обращается |
|---|---|---|
| `content/` | Тексты страниц в Markdown | Каждый файл `.md` превращается в страницу (глава 3) |
| `layouts/` | HTML-шаблоны | По ним строится HTML каждой страницы (глава 4) |
| `assets/` | CSS, картинки для обработки | **Не копируется сам.** Попадает на сайт, только если шаблон вызвал `resources.Get` и что-то с файлом сделал |
| `static/` | Файлы «как есть» | Копируется в `public/` без изменений: `static/admin/index.html` → `/admin/index.html` |
| `data/` | YAML/JSON/TOML с данными | Доступно в шаблонах как `hugo.Data.<имя файла>` |
| `i18n/` | Переводы строк интерфейса | Используется функцией `lang.Translate` (глава 4) |
| `public/` | **Результат сборки** | Создаётся Hugo; в git не хранится |
| `resources/_gen/` | Кеш обработанных картинок и CSS | Создаётся Hugo; ускоряет повторные сборки |

### `assets/` против `static/`

Это различие — одно из главных в Hugo.

- `static/katex/katex.min.css` — уже готовый файл, его не нужно менять. Он лежит в `static/` и копируется как есть.
- `assets/css/main.css` — шаблон `head.html` склеивает его с `syntax.css`, сжимает и добавляет хеш к имени
  (получается `/css/site.min.a2d27922….css`). Поэтому он в `assets/`.
- `assets/uploads/` — фото и картинки из админки. Они в `assets/`, а не в `static/`, чтобы Hugo мог
  уменьшить их и перевести в WebP.

**А если иначе.** Положите `main.css` в `static/css/` — он будет доступен как `/css/main.css`, но
без сжатия и без хеша в имени, а значит, его нельзя кешировать «навсегда» (глава 10): после изменения стилей
браузеры посетителей ещё долго показывали бы старую версию. И наоборот: файл в `assets/`, который
ни один шаблон не запрашивает, на сайт не попадёт вовсе.

### Наложение папок

Hugo не различает «папку проекта» и «папку темы»: он накладывает их друг на друга, и файл проекта
закрывает одноимённый файл темы. Поэтому в любом Hugo-проекте можно переопределить шаблон темы,
положив свой файл с тем же путём (см. главу 1, «Свои шаблоны, а не готовая тема»).

## Разбор `hugo.yaml`

Полный файл:

```yaml
# Всё, что меняется без кода (имя, «обо мне», ссылки, подвал, цвет),
# живёт в data/site.yaml и редактируется через /admin.
# baseURL на проде передаётся из CI: hugo --baseURL "$SITE_URL/".
baseURL: http://localhost:1313/
locale: ru-RU
defaultContentLanguage: ru
title: Персональный сайт
enableRobotsTXT: true

disableKinds: [taxonomy, term]

outputs:
  home: [html]
  section: [html, rss]

permalinks:
  page:
    posts: /posts/:contentbasename/
    projects: /projects/:contentbasename/

markup:
  goldmark:
    parser:
      # Картинка отдельным абзацем → <figure> с подписью (render-image.html)
      wrapStandAloneImageWithinParagraph: false
    renderer:
      unsafe: false
    extensions:
      passthrough:
        enable: true
        delimiters:
          block: [['\[', '\]'], ['$$', '$$']]
          inline: [['\(', '\)']]
  highlight:
    noClasses: false

imaging:
  webp:
    quality: 82
  resampleFilter: lanczos

services:
  rss:
    limit: 30

params:
  # Сколько последних записей показывать на главной
  homePostsLimit: 5
```

Первые строки-комментарии объясняют главное решение: **всё, что владелец меняет сам, вынесено в `data/site.yaml`**.
Админка редактирует только `content/` и `data/`, а `hugo.yaml` остаётся «кодом», который трогает разработчик.

### `baseURL`

Полный адрес корня сайта. Из него строятся абсолютные ссылки: `.Permalink`, `canonical`, `og:url`, ссылки в RSS и `sitemap.xml`.

Здесь записан `http://localhost:1313/` — адрес локального сервера. Настоящий домен в репозиторий не записан:
CI передаёт его флагом (глава 9):

```bash
hugo --gc --minify --baseURL "${SITE_URL%/}/"
```

Флаг командной строки сильнее значения в файле. Плюсы: домен можно сменить в настройках GitHub без коммита,
а тот же репозиторий можно собрать для тестового адреса.

**Проверено:**

| Как собрали | `canonical` у записи |
|---|---|
| `hugo` | `http://localhost:1313/posts/pervoe-obnovlenie/` |
| `hugo --baseURL https://example.com` (без `/` в конце) | `https://example.com/posts/pervoe-obnovlenie/` — Hugo добавил `/` сам |
| `hugo --baseURL https://example.com/site/` | `https://example.com/site/posts/pervoe-obnovlenie/` |

**А если иначе: сайт в подпапке.** Если сайт живёт не в корне домена (`https://example.com/site/`),
важно, как в шаблонах написаны ссылки. **Проверено:** при `baseURL: https://example.com/site/`
ссылки шапки `{{ "/posts/" | relURL }}` превращаются в `/posts/` — подпапка теряется, а CSS
(`$css.RelPermalink`) и ссылки на страницы (`.RelPermalink`) получают правильный `/site/…`.
Если написать путь без ведущего слеша — `{{ "posts/" | relURL }}`, — получится `/site/posts/`.
Этот сайт живёт в корне домена, поэтому разницы нет; но если вы планируете подпапку (например, GitHub Pages
без своего домена: `https://<логин>.github.io/<репозиторий>/`), пишите пути для `relURL` и `absURL` без `/` в начале.

### `locale` и `defaultContentLanguage`

- `locale: ru-RU` — региональные настройки языка. От неё зависят атрибут `<html lang="ru-RU">`
  (в `baseof.html` это `site.Language.Locale`), формат дат в `time.Format ":date_long"`
  и `<language>` в RSS.
- `defaultContentLanguage: ru` — код языка контента. По нему Hugo ищет файл переводов `i18n/ru.yaml`.

**Проверено:** при `locale: en-US` атрибут становится `lang="en-US"`, а дата записи — `March 2, 2026`
вместо `2 марта 2026 г.`. Склонение «2 записи» при этом остаётся русским: оно берётся из `i18n/ru.yaml`
по `defaultContentLanguage`.

**Многоязычный сайт** настраивается блоком `languages:` (у каждого языка свои `locale`, `title`, папка контента
или суффикс файла `index.en.md`). Здесь он не нужен.

### `title`

Название сайта для Hugo. Шаблоны этого проекта его **не используют**: имя в шапке, `<title>` и подвале
берутся из `data/site.yaml` (`name`), чтобы владелец менял его в админке.

**Проверено:** `title` всё же виден в одном месте — во встроенном шаблоне RSS: у ленты `posts/index.xml`
заголовок `Записи on Персональный сайт`. Слово `on` — из встроенного английского шаблона. Если это мешает,
положите свой `layouts/rss.xml` (это тема главы 7).

### `enableRobotsTXT: true`

Hugo создаёт `/robots.txt` по встроенному шаблону: `User-agent: *` — разрешить всем роботам всё.
**Проверено:** без этой строки файла `robots.txt` в `public/` нет. Свой вариант (например, со ссылкой на sitemap)
делается шаблоном `layouts/robots.txt`.

### `disableKinds: [taxonomy, term]`

Hugo умеет «таксономии» — теги и категории: страница `/tags/` со списком тегов (kind `taxonomy`)
и страница `/tags/hugo/` со списком записей с этим тегом (kind `term`). Они включены по умолчанию.

Здесь их отключили: роль группировки играют проекты.

**Проверено:** без этой строки в `public/` появляются папки `tags/` и `categories/`, а сборка выдаёт
`WARN found no layout file for "html" for kind "taxonomy"` — шаблона для них нет.

Другие значения: `home`, `page`, `section`, `rss`, `sitemap`, `robotsTXT`, `404`. Например,
`disableKinds: [sitemap]` убирает `sitemap.xml`.

**А если нужны теги.** Удалите строку, создайте шаблоны `layouts/taxonomy.html` и `layouts/term.html`
и добавьте записям `tags: [hugo, css]` во front matter (и поле в админку).

### `outputs`

Какие форматы создаются для каждого вида страниц. По умолчанию у главной и разделов — `html` и `rss`.

```yaml
outputs:
  home: [html]
  section: [html, rss]
```

- Главной RSS не нужен: всё, на что стоит подписываться, — это записи, у них своя лента `/posts/index.xml`.
- Разделам оставили RSS, но у раздела проектов его убрали в `content/projects/_index.md` строкой `outputs: [html]`
  (глава 3). Итог — ровно одна лента.

**Проверено:** без блока `outputs` в `public/` появляется ещё `/index.xml` (лента главной, в которую попадают
и проекты, и записи). Без `outputs: [html]` в `content/projects/_index.md` появляется `/projects/index.xml`.

Другие форматы: `json` (например, для поиска на JavaScript), `calendar`, `amp`, свои — через `outputFormats`.

### `permalinks`

Как строится адрес обычной страницы (kind `page`) в разделе:

```yaml
permalinks:
  page:
    posts: /posts/:contentbasename/
    projects: /projects/:contentbasename/
```

`:contentbasename` — имя папки бандла (`content/posts/pervoe-obnovlenie/index.md` → `pervoe-obnovlenie`).
Подробно — в главе 3. Здесь важно: адрес жёстко равен имени папки, и поле `slug` в front matter не может его поменять.

Другие токены: `:year`, `:month`, `:day`, `:title`, `:slug`, `:section`, `:filename`.
**Проверено:** `posts: /:year/:month/:contentbasename/` даёт `/2026/03/pervoe-obnovlenie/`,
а `posts: /posts/:title/` — `/posts/первое-обновление/` (кириллица в адресе; при смене заголовка меняется адрес и ломаются ссылки).

### `markup`

Настройки превращения Markdown в HTML. Подробно — в главе 5, здесь кратко.

- `goldmark` — движок Markdown в Hugo.
  - `parser.wrapStandAloneImageWithinParagraph: false` — картинка отдельным абзацем не оборачивается в `<p>`,
    и render-хук картинок может сделать из неё `<figure>` с подписью. **Проверено:** при `true`
    картинка выходит как `<p><img …></p>`, без `<figure>` и подписи.
  - `renderer.unsafe: false` — HTML-теги внутри Markdown вырезаются. **Проверено:** `<div class="x">raw</div>`
    в тексте записи заменяется на `<!-- raw HTML omitted -->`, а сборка печатает предупреждение.
    Это защита: текст пишется в админке, и в него нельзя случайно (или нарочно) вставить `<script>`.
    `true` разрешает HTML как есть.
  - `extensions.passthrough` — фрагменты между `\(` и `\)`, `\[` и `\]`, `$$` и `$$` Goldmark не трогает
    (не превращает `_` в курсив) и передаёт в render-хук формул.
- `highlight.noClasses: false` — подсветка кода размечается классами (`<span class="k">def</span>`),
  а цвета задаёт `assets/css/syntax.css`, в том числе отдельные для тёмной темы. **Проверено:** при `true`
  цвета вписываются прямо в HTML (`<pre style="color:#f8f8f2;background-color:#272822;…">`, стиль monokai),
  и тёмную тему для кода сделать уже нельзя.

### `imaging`

Настройки обработки картинок (глава 5):

- `webp.quality: 82` — качество сжатия WebP от 1 до 100. **Проверено:** картинка `chart.png` из демо-записи
  при 82 весит 8410 байт, при 40 — 4470 байт. Ниже ~75 на фотографиях становятся заметны артефакты; 80–85 —
  обычный компромисс. Для JPEG есть отдельный `imaging.quality`.
- `resampleFilter: lanczos` — алгоритм уменьшения. `lanczos` — самый чёткий, но медленный; по умолчанию стоит
  `box` (быстрый, чуть мягче). Результат кешируется в `resources/_gen/`, поэтому медленный фильтр
  замедляет только первую сборку.

### `services.rss.limit: 30`

Сколько последних записей попадает в RSS-ленту. По умолчанию — без ограничения: со временем лента разрастается.
**Проверено:** при `limit: 1` в `posts/index.xml` остаётся один `<item>`.

### `params`

Свои параметры, которых нет в Hugo. В шаблонах — `site.Params.<имя>`:

```yaml
params:
  # Сколько последних записей показывать на главной
  homePostsLimit: 5
```

Используется в `home.html` (глава 4).

**Чем `params` отличается от `data/site.yaml`.** И то и другое — данные для шаблонов. Но `hugo.yaml` админка не редактирует.
Сюда кладут то, что меняет разработчик; в `data/` — то, что меняет владелец.

**Переменные окружения.** Любую настройку можно переопределить переменной `HUGO_<ПУТЬ>`.
**Проверено:** `HUGO_PARAMS_HOMEPOSTSLIMIT=1 hugo` — на главной одна запись и ссылка «Все записи →».
Так CI или локальный запуск может менять настройки, не трогая файл.

### Как посмотреть итоговые настройки

```bash
hugo config               # все настройки с учётом значений по умолчанию, в TOML
hugo config --format yaml # то же в YAML
```

Полезно, когда непонятно, какое значение реально действует. Имена выводятся в нижнем регистре:
`baseurl = 'http://localhost:1313/'`, `disablekinds = ['taxonomy', 'term']`.

## Команды

### `hugo server` — разработка

```bash
hugo server --buildDrafts --disableFastRender
```

Запускает сервер на `http://localhost:1313` с живой перезагрузкой: сохранили файл — страница в браузере
обновилась сама. Сайт собирается в память, в `public/` ничего не пишется.

| Флаг | Что делает | Зачем здесь |
|---|---|---|
| `--buildDrafts`, `-D` | Включает страницы с `draft: true` | Видеть черновики локально; на проде их нет |
| `--disableFastRender` | При изменении пересобирает весь сайт, а не только открытую страницу | Здесь страницы зависят друг от друга: правка записи меняет хронологию проекта и главную. Быстрый режим мог бы показать устаревший список |
| `--buildFuture`, `-F` | Включает страницы с датой в будущем | Проверить запланированную запись |
| `--buildExpired`, `-E` | Включает страницы с истёкшим `expiryDate` | Здесь не используется |
| `--navigateToChanged`, `-N` | Браузер сам переходит на страницу, файл которой вы изменили | Удобно при правке многих записей |
| `--port`, `-p` | Порт (по умолчанию 1313) | Если 1313 занят |
| `--bind 0.0.0.0` | Слушать все интерфейсы, а не только `127.0.0.1` | Открыть сайт с телефона в той же сети (вместе с `--baseURL http://<IP>:1313/`) |

### `hugo --gc --minify` — сборка как на проде

- Без подкоманды `hugo` собирает сайт в `public/` (или в папку из флага `-d`).
- `--minify` сжимает HTML, CSS, XML, JSON: убирает лишние пробелы, переводы строк, кавычки атрибутов.
  **Проверено:** главная весит 3271 байт без флага и 3019 с ним. Выигрыш небольшой, но бесплатный.
  Из-за него в собранном HTML атрибуты без кавычек (`<html lang=ru-RU>`) — это допустимый HTML.
- `--gc` (garbage collection) после сборки удаляет из `resources/_gen/` файлы, которые больше не нужны:
  например, уменьшенные копии удалённой картинки. **Проверено:** подброшенный в `resources/_gen/images/`
  лишний файл после `hugo --gc` исчез, а нужные `*_hu_*.webp` остались.

Полезные флаги для отладки — в главе 12: `--printPathWarnings`, `--templateMetrics`, `--panicOnWarning`.

## `.gitignore`

```
/public/
/resources/_gen/
.hugo_build.lock
.DS_Store
```

- `/public/` — результат сборки. Он собирается из исходников, хранить его в git незачем: появились бы огромные
  диффы на каждую правку и конфликты.
- `/resources/_gen/` — кеш. Некоторые проекты его коммитят, чтобы CI не обрабатывал картинки заново;
  здесь картинок мало, и проще держать репозиторий чистым.
- `.hugo_build.lock` — файл-замок, который Hugo создаёт на время сборки.
- `.DS_Store` — служебные файлы macOS Finder.

Слеш в начале (`/public/`) означает «только в корне»: папка `content/posts/public/` не будет проигнорирована.

## `Makefile`

```make
HUGO ?= hugo

.PHONY: dev build clean

dev: ## Локальный сервер с черновиками: http://localhost:1313
	$(HUGO) server --buildDrafts --disableFastRender

build: ## Сборка в public/ как на проде
	$(HUGO) --gc --minify

clean:
	rm -rf public resources/_gen .hugo_build.lock
```

`make` здесь — просто записная книжка команд: не нужно помнить флаги.

- `HUGO ?= hugo` — переменная со значением по умолчанию. `?=` присваивает, только если переменная ещё не задана.
  Поэтому можно запустить другой Hugo, не меняя файл: `make build HUGO=~/bin/hugo-0.169`.
  **Проверено:** `make -n build HUGO=/путь/к/hugo` печатает `/путь/к/hugo --gc --minify`
  (`-n` — показать команды, не выполняя). Переменная окружения тоже работает: `HUGO=/x make -n build` печатает `/x --gc --minify`.
  **Проверено:** с `=` вместо `?=` та же команда печатает `hugo --gc --minify` — переменная окружения игнорируется
  (значение из командной строки `make build HUGO=…` всё равно победило бы).
- `.PHONY: dev build clean` — эти цели не файлы. Без этой строки, если в корне появится файл или папка `build`,
  `make build` ответит «`build` is up to date» и ничего не сделает.
- `## …` после цели — просто комментарий для человека. Часто к таким комментариям добавляют цель `help`,
  которая их печатает:

  ```make
  help:
  	@grep -E '^[a-z]+:.*## ' $(MAKEFILE_LIST) | sed 's/:.*## /\t/'
  ```

  **Проверено:** `make help` печатает `dev  Локальный сервер…` и `build  Сборка в public/…`
  (у `clean` комментария нет, поэтому её в списке нет). В проекте такой цели нет — целей всего три.
- Команды внутри цели начинаются с **табуляции**, а не пробелов. С пробелами `make` выдаст `missing separator`.

## Где ещё пригодится

- `HUGO_<ПАРАМЕТР>` и `--baseURL` — собирать один репозиторий для нескольких окружений (тест и прод).
- `assets/` + `resources.Get` — любой файл, который надо обработать: SCSS, JS (через `js.Build`), картинки.
- `Makefile` с `?=` — стандартный способ дать короткие команды любому проекту, не только на Hugo.

## Упражнения

1. Запустите `make dev`, откройте `http://localhost:1313`, поменяйте `homePostsLimit` на `1` — что изменилось на главной?
2. Соберите сайт с `--baseURL https://example.com/blog/` и найдите в `public/index.html` ссылки,
   которые потеряли `/blog/`. Поправьте `header.html` так, чтобы они работали.
3. Удалите `disableKinds` и добавьте одной записи `tags: [тест]`. Какие страницы появились? Почему Hugo
   ругается на отсутствие шаблона?
4. Сравните размер `public/` после `hugo` и `hugo --minify` (`du -sh public`).

## Итог

Hugo — один файл программы; ставьте ту же extended-версию, что в CI. `content/` — тексты, `layouts/` — шаблоны,
`assets/` — то, что обрабатывается, `static/` — то, что копируется как есть, `data/` — данные для шаблонов.
`hugo.yaml` задаёт адреса, форматы и обработку Markdown, а всё, что меняет владелец, вынесено в `data/site.yaml`.
Для работы — `make dev`, для проверки перед публикацией — `make build`.
