# Глава 11. Выпуски и откат

## Зачем

Самый простой деплой — скопировать `public/` поверх папки сайта: `rsync -r public/ server:/var/www/site/`.
У него три проблемы:

1. **Полуобновлённый сайт.** Копирование длится секунды. В это время посетитель может получить новый HTML,
   который ссылается на CSS, ещё не докачанный, — или старый HTML со ссылкой на уже удалённую картинку.
2. **Нечем откатиться.** Старые файлы перезаписаны. Если новая версия плохая, нужно чинить код и ждать новой сборки.
3. **Сбой посередине.** Оборвалась связь — на сервере смесь двух версий, и так до следующего деплоя.

Решение, которое используют от Capistrano до Kubernetes, — **выпуски** (releases):

```
/var/www/site/
├── current -> releases/4f3949548aa0     ← Caddy отдаёт отсюда (глава 10)
└── releases/
    ├── initial/                         ← заглушка от setup-server.sh
    ├── e1f90a0c1d2b/
    └── 4f3949548aa0/                     ← имя = 12 символов хеша коммита (глава 9)
```

Каждая сборка копируется в **свою новую папку**. Пока она заливается, сайт работает из старой.
Когда всё на месте, **одним атомарным действием** переключается симлинк `current`. Откат — переключить симлинк назад.

## Как сделано здесь: `deploy/publish.sh`

Запускается в GitHub Actions (глава 9): `bash deploy/publish.sh public "deploy@host" "${GITHUB_SHA::12}"`.

```bash
#!/usr/bin/env bash
# Атомарная выкладка собранного сайта на сервер.
#   deploy/publish.sh <папка-сборки> <user@host> <имя-релиза>
# Каждый релиз — отдельная папка в /var/www/site/releases, «current» — симлинк
# на активный. Переключение мгновенное, откат — rollback.sh на сервере.
set -euo pipefail

SRC=${1:?папка сборки}
DEST=${2:?user@host}
RELEASE=${3:-$(date +%Y%m%d%H%M%S)}
ROOT=/var/www/site
KEEP=5

RSH=${RSYNC_RSH:-ssh}

# Неизменённые файлы берутся жёсткими ссылками из текущего релиза — быстро и без лишнего места.
rsync -rlz --checksum --delete \
  --link-dest="$ROOT/current/" \
  "$SRC/" "$DEST:$ROOT/releases/$RELEASE/"

$RSH "$DEST" bash -s -- "$ROOT" "$RELEASE" "$KEEP" <<'REMOTE'
set -euo pipefail
ROOT=$1 RELEASE=$2 KEEP=$3
ln -sfn "releases/$RELEASE" "$ROOT/current.tmp"
mv -Tf "$ROOT/current.tmp" "$ROOT/current"
cd "$ROOT/releases"
ls -1t | tail -n +$((KEEP + 1)) | xargs -r rm -rf --
echo "Активный релиз: $RELEASE"
REMOTE
```

## Как это проверялось

Сервера с SSH в учебной песочнице не было, поэтому скрипт прогоняли локально: `ROOT` заменили на временную папку,
а в `RSYNC_RSH` подставили маленький скрипт, который вместо подключения по SSH выполняет команду на этой же машине.
Логика `publish.sh` и `rollback.sh` при этом не менялась. Все пометки **«Проверено»** ниже — из этого прогона
(rsync 3.2.7, GNU coreutils 9.4) на настоящей сборке сайта (`hugo --gc --minify`, 40 файлов, 528 КБ).

## Разбор

### Аргументы

```bash
SRC=${1:?папка сборки}
DEST=${2:?user@host}
RELEASE=${3:-$(date +%Y%m%d%H%M%S)}
ROOT=/var/www/site
KEEP=5
RSH=${RSYNC_RSH:-ssh}
```

- `${1:?…}` — обязательный аргумент (глава 10).
- `${3:-$(date +%Y%m%d%H%M%S)}` — имя выпуска; если не передано, текущее время: `20261030120000`.
  Удобно, если запускать скрипт руками со своего компьютера.
- `ROOT`, `KEEP` — константы в начале файла: путь на сервере и сколько выпусков хранить.
- `RSH=${RSYNC_RSH:-ssh}` — та же команда подключения, что использует `rsync`. В CI это `ssh -i ~/.ssh/id_deploy -o IdentitiesOnly=yes`;
  при ручном запуске — просто `ssh` с вашими ключами.

### Копирование: `rsync`

```bash
rsync -rlz --checksum --delete \
  --link-dest="$ROOT/current/" \
  "$SRC/" "$DEST:$ROOT/releases/$RELEASE/"
```

`rsync` копирует файлы по сети и умеет не передавать то, что на той стороне уже есть.

| Флаг | Что делает | Если убрать или заменить |
|---|---|---|
| `-r` | рекурсивно, со всеми подпапками | не скопируется ничего: для источника `public/` rsync пишет «skipping directory .» (**проверено**) |
| `-l` | симлинки копировать как симлинки | симлинки пропустятся с предупреждением. В сборке Hugo их нет, флаг — на будущее |
| `-z` | сжимать при передаче | дольше по медленному каналу; на быстром почти не заметно |
| `--checksum` | сравнивать файлы по содержимому (хешу) | см. ниже — без него жёсткие ссылки не работают |
| `--delete` | удалить в приёмнике файлы, которых нет в источнике | см. ниже |
| `--link-dest=DIR` | если файл совпадает с файлом в `DIR`, сделать на него жёсткую ссылку вместо копии | каждый выпуск — полная копия сайта |

Чего здесь **нет** и почему:

- **`-a`** (архивный режим = `-rlptgoD`). Он добавил бы `-p` (права), `-t` (время изменения), `-g -o` (группа и владелец —
  для них нужен root на сервере), `-D` (устройства). Права и владелец берутся из настроек сервера: новые файлы
  принадлежат `deploy`, права — по умолчанию (644/755), Caddy их читает. Время изменения не нужно — см. `--checksum`.
- **`-v`** — подробный список файлов. Для отладки добавьте `-v` или `--itemize-changes` (`-i`): по строке на каждый файл
  с причиной, почему он передан.

#### `--link-dest` и жёсткие ссылки

**Жёсткая ссылка** — второе имя того же файла на диске. Данные хранятся один раз, а видны по двум путям:
`releases/A/index.html` и `releases/B/index.html`. Счётчик ссылок (`stat -c %h`) показывает, сколько имён у файла.
Удаление одного имени не трогает другие; место освобождается, когда удалено последнее.

С `--link-dest="$ROOT/current/"` rsync для каждого файла смотрит в активный выпуск: если там лежит такой же файл,
в новом выпуске создаётся жёсткая ссылка на него — ничего не передаётся по сети и не занимает места.
Передаются только изменившиеся файлы.

**Проверено:**

| Шаг | Размер нового выпуска | Счётчик ссылок `index.html` |
|---|---|---|
| Первый выпуск `r1` (до него — только заглушка `initial`) | 528 КБ | 1 — всё скопировано |
| `r2` из той же сборки | 40 КБ (только папки) | 2 — общий файл с `r1` |
| `r3`: изменён `index.html`, у `robots.txt` обновлено только время изменения | 44 КБ | `index.html` — 1 (новый файл), `robots.txt` — 3 (общий с `r1`, `r2`) |

Путь в `--link-dest` — **на сервере** (абсолютный). Если такой папки нет (например, первый деплой без заглушки),
rsync предупредит и просто скопирует всё.

#### Почему `--checksum`

По умолчанию rsync считает файлы одинаковыми, если совпадают **размер и время изменения** — это быстро.
Но в CI каждая сборка создаёт файлы заново: у всех файлов новое время изменения, даже если содержимое то же.
К тому же без `-t` rsync не переносит время изменения, и у файлов в выпусках оно своё. По размеру и времени
**ни один** файл не совпал бы, и `--link-dest` не нашёл бы ни одной пары.

`--checksum` сравнивает содержимое. Это дороже (rsync читает файлы на обеих сторонах), но сайт в несколько мегабайт
читается за доли секунды.

**Проверено:** тот же прогон, что `r3`, но без `--checksum`: ни одной жёсткой ссылки, новый выпуск — снова 528 КБ.
А с `--checksum` у `robots.txt`, которому обновили только время изменения (`touch`), ссылка сохранилась.

#### `--delete`

Новый выпуск — пустая папка, удалять там нечего. Флаг нужен на случай, когда папка выпуска **уже существует**:
повторный запуск workflow для того же коммита даёт то же имя выпуска. Тогда `--delete` убирает файлы, которых нет в сборке.

**Проверено:** в папку активного выпуска подложили лишний `stale.txt` и выложили тот же выпуск повторно —
файл удалён, в выпуске ровно 40 файлов, как в сборке.

Обратите внимание: это единственный случай, когда rsync пишет **в активный выпуск** (`current` указывает на ту же папку).
Содержимое сборки то же самое, поэтому на практике это безопасно, но атомарности здесь нет.

#### Слэши в конце путей

`"$SRC/"` — со слэшем: копировать **содержимое** `public/`, а не саму папку. **Проверено:** `rsync -r src d1` даёт
`d1/src/a/f`, а `rsync -r src/ d2` — `d2/a/f`. Без слэша сайт оказался бы в `releases/<выпуск>/public/`,
и Caddy отдавал бы 404 на главной.

Слэш в конце приёмника и `--link-dest` — для ясности (это папки); на поведение он не влияет.

### Переключение: удалённый скрипт

```bash
$RSH "$DEST" bash -s -- "$ROOT" "$RELEASE" "$KEEP" <<'REMOTE'
...
REMOTE
```

- `ssh host команда` выполняет команду на сервере. Команда здесь — `bash -s`: «читай скрипт со стандартного ввода».
- `-- "$ROOT" "$RELEASE" "$KEEP"` — аргументы этому скрипту, внутри они `$1 $2 $3`. `--` отделяет их от опций bash.
- `<<'REMOTE' … REMOTE` — **heredoc**: текст между метками подаётся на стандартный ввод, то есть уходит по SSH
  и выполняется на сервере. Скрипт для сервера лежит прямо в `publish.sh` — не нужно заранее копировать его на сервер.
- **Кавычки вокруг `'REMOTE'`** — важная деталь. С кавычками текст передаётся как есть. Без них локальный bash
  **сначала** подставил бы в текст свои переменные — `$1`, `$2`, `$ROOT` — и на сервер ушёл бы уже испорченный скрипт.

  **Проверено:** тот же heredoc с кавычками печатает `ROOT=/var/www/site RELEASE=r9`, без кавычек — `ROOT= RELEASE=`:
  `$1` и `$2` подставились из окружения запускающего скрипта, где они пустые.

```bash
set -euo pipefail
ROOT=$1 RELEASE=$2 KEEP=$3
```

Строгий режим и на сервере: если что-то не так, скрипт остановится, и `ssh` вернёт ошибку — шаг в GitHub Actions покраснеет.

### Атомарная замена симлинка

```bash
ln -sfn "releases/$RELEASE" "$ROOT/current.tmp"
mv -Tf "$ROOT/current.tmp" "$ROOT/current"
```

**Атомарная** операция — та, что происходит целиком или не происходит вовсе, без промежуточного состояния.
Нужно, чтобы в любой момент `current` указывал либо на старый выпуск, либо на новый — но существовал.

1. `ln -sfn цель current.tmp` — создать симлинк под временным именем. `-s` — символическая ссылка, `-f` — заменить,
   если `current.tmp` остался от прошлого сбоя, `-n` — не заходить внутрь, если `current.tmp` уже ссылка на папку
   (иначе новая ссылка создалась бы **внутри** старого выпуска).
2. `mv -Tf current.tmp current` — переименовать временный симлинк в `current`. Переименование в пределах одной файловой системы —
   системный вызов `rename(2)`, который **атомарно** подменяет существующий `current`.
   - `-T` — считать `current` файлом, а не папкой. Без `-T`, поскольку `current` — ссылка на папку, `mv` **переложил бы**
     `current.tmp` внутрь активного выпуска, а `current` не переключился бы.
     **Проверено:** `mv -f x.tmp cur` (где `cur` — ссылка на папку `a`) создал `a/x.tmp`, а `cur` остался указывать на `a`.
   - `-f` — не спрашивать подтверждения.

**А почему не просто `ln -sfn releases/$RELEASE current`?** Традиционно `ln -f` сначала удаляет старую ссылку, а потом
создаёт новую — между этими действиями `current` не существует, и Caddy отвечает 404. Свежие GNU coreutils
делают это аккуратнее. **Проверено** через `strace` на coreutils 9.4: `ln -sfn` сам создаёт ссылку под случайным
временным именем и переименовывает её (`symlinkat` → `renameat`). Но на старых системах, в BusyBox или на macOS это
не гарантировано. Связка «временная ссылка + `mv -T`» атомарна везде, где есть `rename(2)`, поэтому используется она.

Ещё одно следствие: ссылка **относительная** (`releases/…`). Её можно создавать и проверять внутри любой копии папки.

### Чистка старых выпусков

```bash
cd "$ROOT/releases"
ls -1t | tail -n +$((KEEP + 1)) | xargs -r rm -rf --
```

- `ls -1t` — имена по одному в строке (`-1`), новые сверху (`-t`, по времени изменения).
- `tail -n +6` — со строки 6 до конца, то есть всё, кроме пяти самых новых. `$((KEEP + 1))` — арифметика bash.
- `xargs -r rm -rf --` — удалить эти папки. `-r` — **не запускать** команду, если список пуст;
  `--` — конец опций `rm`: имя папки, начинающееся с `-`, не превратится в опцию.

**Проверено:** из семи папок `r1…r7` (`r7` новее всех) конвейер выбирает ровно `r2 r1`.
`xargs` без `-r` на пустом вводе всё равно запускает команду один раз (`rm -rf --` без аргументов безвреден,
но в общем случае это ловушка), а с `-r` — нет.

Чистка идёт **после** переключения: новый выпуск уже активен, и он самый новый — удалить его конвейер не может.
Благодаря жёстким ссылкам удаление старого выпуска освобождает только те файлы, которых нет в других выпусках.

**А если иначе:** `KEEP=20` — больше точек отката, место почти не растёт (общие файлы хранятся один раз).
Хранить «всё» — убрать строку; через год папок будут сотни, и `rollback` без аргумента станет менее понятным.

## Как сделано здесь: `deploy/rollback.sh`

Устанавливается на сервер как `/usr/local/bin/site-rollback` (`setup-server.sh`, глава 10).

```bash
#!/usr/bin/env bash
# Откат на предыдущий релиз (или на указанный): site-rollback [имя-релиза]
set -euo pipefail
ROOT=/var/www/site
cd "$ROOT/releases"
CURRENT=$(basename "$(readlink "$ROOT/current")")
TARGET=${1:-$(ls -1t | grep -vxF "$CURRENT" | head -n 1)}
[ -d "$TARGET" ] || { echo "Нет релиза $TARGET. Есть: $(ls -1t | tr '\n' ' ')"; exit 1; }
ln -sfn "releases/$TARGET" "$ROOT/current.tmp"
mv -Tf "$ROOT/current.tmp" "$ROOT/current"
echo "Было: $CURRENT → стало: $TARGET"
```

Запуск: `sudo -u deploy site-rollback` (от имени `deploy`, чтобы новый симлинк принадлежал ему).

- `readlink current` — куда указывает симлинк (`releases/4f3949548aa0`), `basename` — последняя часть (`4f3949548aa0`).
- `${1:-…}` — указанный выпуск, а если не указан — самый новый, кроме текущего:
  `grep -vxF "$CURRENT"` — убрать строку, **целиком** (`-x`) и **буквально** (`-F`) равную текущему (`-v` — инверсия),
  `head -n 1` — первая из оставшихся.
- `[ -d "$TARGET" ] || { …; exit 1; }` — защита от опечатки: если такой папки нет, вывести список и выйти,
  **ничего не переключая**. Без проверки `current` стал бы ссылкой в никуда, и весь сайт отвечал бы 404.
- Переключение — та же атомарная пара `ln` + `mv -T`.

**Проверено:** при выпусках `r3…r7` и активном `r7` команда без аргумента переключила на `r6`, `site-rollback r5` — на `r5`,
`site-rollback nope` вывел «Нет релиза nope. Есть: r7 r6 r5 r4 r3» и завершился с кодом 1, ничего не изменив.

### Тонкость: повторный откат без аргумента

«Самый новый, кроме текущего» — это не «на шаг назад от текущего». После отката на `r6` повторный `site-rollback`
без аргумента выберет самый новый, кроме `r6`, — то есть вернёт **`r7`**, а не перейдёт на `r5`.

**Проверено:** при активном `r5` команда без аргумента переключила на `r7`.

Поэтому для отката больше чем на один шаг называйте выпуск явно:

```bash
ls -1t /var/www/site/releases        # список, новые сверху
sudo -u deploy site-rollback e1f90a0c1d2b
```

Имя выпуска — начало хеша коммита, так что нужный легко найти в истории репозитория: `git log --oneline`.

### После отката

Откат меняет только сервер. Следующий push в `main` выложит новый выпуск как обычно — и плохая версия вернётся,
если её не исправить в репозитории. Правильный порядок: откатиться (сайт сразу работает), затем `git revert`
плохого коммита и push.

## А если иначе: другие схемы выкладки

| Схема | Как устроена | Когда лучше |
|---|---|---|
| Копирование поверх (`rsync --delete` в `/var/www/site`) | Одна папка | Никогда для публичного сайта — см. «Зачем» |
| **Выпуски + симлинк** (здесь) | Папка на выпуск, атомарное переключение | Один сервер, статика или простое приложение |
| Blue/green | Два полных окружения (например, два сервера), переключение балансировщиком | Приложения с базой данных, нужна проверка новой версии под реальной нагрузкой перед переключением |
| Хостинг статики (Pages, Netlify, Cloudflare) | То же самое, но делает сервис | Когда свой сервер не нужен (глава 1) |

Возможные доработки этой схемы:

- **Проверка перед переключением.** Между `rsync` и `mv` добавить `test -s "$ROOT/releases/$RELEASE/index.html"`:
  пустая или битая сборка не станет активной.
- **Защита от одновременного запуска** на стороне сервера: обернуть удалённую часть в `flock /var/www/site/.lock …`.
  Сейчас эту роль выполняет `concurrency` в GitHub Actions (глава 9), но ручной запуск со своего компьютера её обходит.
- **Старые файлы для открытых вкладок.** Посетитель открыл страницу до деплоя, а картинку с хешем в имени
  подгружает после — в новом выпуске её уже нет. Для статического сайта это редкость (страница грузится целиком
  за доли секунды), но для тяжёлых сайтов файлы с хешем копируют в общую папку, которая не чистится вместе с выпусками.

## Где ещё пригодится

- Тот же приём «собрать в новую папку → атомарно переключить симлинк» подходит для любых конфигов и приложений:
  PHP-сайтов, Python-приложений (`current/` + перезапуск службы), даже для обновления больших справочников данных.
- `rsync --link-dest` — основа инкрементальных резервных копий (так работают Time Machine-подобные скрипты):
  каждая копия выглядит полной, а места занимает только разница.
- Временный файл + `mv` — стандартный способ атомарно записать любой файл: сначала `config.json.tmp`, затем `mv` поверх.
  Читающая программа никогда не увидит полузаписанный конфиг.

## Упражнения

1. Создайте локально папку `site/releases/{a,b}` с разными `index.html` и симлинк `site/current -> releases/a`.
   В одном терминале запустите `while true; do cat site/current/index.html >/dev/null || echo ПРОПАЛ; done`,
   в другом переключайте выпуски парой `ln -sfn … current.tmp && mv -Tf current.tmp current` в цикле.
   Появляется ли «ПРОПАЛ»? Попробуйте вместо этого `rm current && ln -s releases/b current`.
2. Сделайте две сборки сайта с разницей в одной записи и выложите их `rsync --link-dest` в соседние папки.
   Сравните `du -sh` каждой папки по отдельности и обеих вместе. Найдите общие файлы через `stat -c '%h %i %n'`.
3. Измените `rollback.sh` так, чтобы без аргумента он брал выпуск, **предшествующий** текущему по времени,
   а не самый новый. Проверьте два отката подряд.

## Итог

Каждый деплой — новая папка выпуска, в которую rsync передаёт только изменившиеся файлы, а остальные берёт
жёсткими ссылками из активного выпуска (`--link-dest` + `--checksum`). Когда папка готова, симлинк `current`
атомарно переключается переименованием (`ln` во временное имя + `mv -T`), посетители не видят промежуточного
состояния. Хранятся пять последних выпусков; `site-rollback` переключает обратно за секунду — с одной тонкостью:
без аргумента он выбирает самый новый выпуск, кроме текущего.
