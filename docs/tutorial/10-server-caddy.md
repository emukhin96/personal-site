# Глава 10. Сервер и Caddy

## Зачем

Собранный сайт — папка файлов. Чтобы он открывался по `https://ваш-домен`, нужны:

1. **Компьютер в интернете** с постоянным IP-адресом — VPS (виртуальный сервер), например у Hetzner.
2. **Домен**, который указывает на этот IP (DNS).
3. **Веб-сервер**, который отвечает на HTTP-запросы файлами из папки и умеет HTTPS.
4. **Доступ для деплоя**: GitHub Actions должен заходить на сервер и класть файлы, но не получать права root.

Всё это настраивается один раз скриптом `deploy/setup-server.sh` и конфигом `deploy/Caddyfile`.

## Подготовка: VPS, DNS, ключи

### VPS

Подойдёт самый маленький тариф с Debian или Ubuntu: статический сайт почти не нагружает процессор,
а 20 ГБ диска хватит на тысячи записей с картинками. При создании сервера добавьте свой SSH-ключ —
тогда вход для root будет по ключу, а не по паролю.

### DNS

В панели регистратора домена (или в DNS-сервисе, например Cloudflare) добавьте записи:

| Тип | Имя | Значение | Зачем |
|---|---|---|---|
| `A` | `@` (сам домен) | IPv4 сервера | основной адрес |
| `AAAA` | `@` | IPv6 сервера | если у сервера есть IPv6 |
| `A` / `AAAA` | `www` | те же адреса | если нужен `www.домен` — Caddy перенаправит его на основной |

Записи расходятся по миру от минут до нескольких часов. Проверка: `dig +short ваш-домен` должен вернуть IP сервера.

**А если иначе:** если `AAAA` указывает на IPv6, который сервер не слушает (или это старый адрес), часть посетителей
и сам Let's Encrypt будут ходить по IPv6 и получать ошибку. Нет IPv6 — не создавайте `AAAA` вовсе.
Если включить «оранжевое облако» Cloudflare (проксирование), посетители будут ходить через Cloudflare, и
Caddy получит сертификат по-прежнему, но заголовки кеша и HTTPS придётся согласовывать с настройками Cloudflare.

### Ключ для деплоя

```bash
ssh-keygen -t ed25519 -f ~/.ssh/site_deploy -C github-deploy -N ''
```

- `-t ed25519` — тип ключа. Короткий, быстрый, современный; поддерживается всеми актуальными OpenSSH.
  Альтернатива `-t rsa -b 4096` — для очень старых серверов.
- `-f ~/.ssh/site_deploy` — имя файла. Получатся `site_deploy` (приватный, уйдёт в секрет `DEPLOY_SSH_KEY`)
  и `site_deploy.pub` (публичный, уйдёт на сервер).
- `-C github-deploy` — комментарий в конце публичного ключа. Помогает понять в `authorized_keys`, чей это ключ.
- `-N ''` — пустая парольная фраза. Нужна, потому что GitHub Actions не сможет её ввести.
  Компенсируется тем, что ключ отдельный, только для деплоя, и пускает только пользователя `deploy`.

**Почему отдельный ключ, а не ваш личный.** Если секрет утечёт, достаточно удалить одну строку из
`/home/deploy/.ssh/authorized_keys` — ваш доступ к серверу и другим машинам не пострадает.

## Как сделано здесь: `deploy/setup-server.sh`

Запускается один раз от root (`README.md` → «Деплой»):

```bash
scp -r deploy root@<IP>:/root/site-deploy
ssh root@<IP> "bash /root/site-deploy/setup-server.sh <домен> '$(cat ~/.ssh/site_deploy.pub)'"
```

`$(cat …)` выполняется **на вашем компьютере**, и содержимое публичного ключа подставляется в команду как второй аргумент.

### Разбор

```bash
#!/usr/bin/env bash
set -euo pipefail

DOMAIN=${1:?домен, например example.com}
DEPLOY_KEY=${2:?публичный SSH-ключ для GitHub Actions}
```

- **`#!/usr/bin/env bash`** — запускать через `bash`, где бы он ни лежал.
- **`set -euo pipefail`** — «строгий режим», стоит во всех скриптах проекта:
  - `-e` — остановиться на первой команде, завершившейся ошибкой. Без него скрипт продолжил бы после
    неудачного `apt-get install caddy` и дошёл бы до `systemctl reload caddy`;
  - `-u` — ошибка при обращении к неопределённой переменной. Опечатка `$DOMIAN` не превратится в пустую строку;
  - `-o pipefail` — конвейер `a | b` считается упавшим, если упала любая его часть, а не только последняя.
    Без этого `curl … | gpg --dearmor …` «успешен», даже если `curl` ничего не скачал.
- **`${1:?текст}`** — первый аргумент или, если его нет, ошибка с этим текстом и выход.
  **Проверено:** без аргументов скрипт печатает `line 3: 1: домен` и завершается с кодом 1, ничего не начав делать.
  Родственные формы: `${1:-значение}` — значение по умолчанию (используется в `publish.sh`), `${1:=значение}` — то же, но с присваиванием.

```bash
apt-get update
apt-get install -y debian-keyring debian-archive-keyring apt-transport-https curl gnupg rsync
```

Пакеты для подключения стороннего репозитория (`gnupg`, ключи, `apt-transport-https`) и **`rsync`**.
`rsync` нужен **на обеих сторонах**: на сервере запускается его серверная часть. Без него деплой упадёт
с «rsync: command not found». `-y` — не спрашивать подтверждения.

```bash
if ! command -v caddy >/dev/null; then
  curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/gpg.key \
    | gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
  curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt \
    > /etc/apt/sources.list.d/caddy-stable.list
  apt-get update
  apt-get install -y caddy
fi
```

Установка Caddy из его официального репозитория пакетов (так рекомендует документация Caddy).

- `command -v caddy` — есть ли уже такая команда. Скрипт **идемпотентный**: второй запуск ничего не сломает
  и не переустановит. Так же сделаны проверки ниже.
- `curl -1sLf`: `-1` — TLS не ниже 1.0 (запрет на устаревший SSL), `-s` — тихо, `-L` — по редиректам, `-f` — ошибка на 404.
- `gpg --dearmor` — переводит ключ подписи из текстового вида в двоичный, как ждёт apt.
  `/usr/share/keyrings/…` — место для ключей сторонних репозиториев. Файл `.list` ссылается на ключ через
  `signed-by=`, поэтому ключ доверен **только** для пакетов этого репозитория, а не для всей системы.
- `apt-get install caddy` ставит Caddy как службу systemd: он запускается при загрузке, работает от пользователя
  `caddy` и читает `/etc/caddy/Caddyfile`.

**А если иначе:** `apt-get install caddy` из стандартного репозитория Debian/Ubuntu — тоже работает, но версия там
может быть старой. Например, `handle_errors 404` (ниже) с кодами ответа в аргументах есть только в свежих Caddy.

```bash
id deploy >/dev/null 2>&1 || useradd --create-home --shell /bin/bash deploy
install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
grep -qxF "$DEPLOY_KEY" /home/deploy/.ssh/authorized_keys 2>/dev/null \
  || echo "$DEPLOY_KEY" >> /home/deploy/.ssh/authorized_keys
chown deploy:deploy /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys
```

- `id deploy || useradd …` — создать пользователя, если его нет. `a || b` — «выполнить `b`, только если `a` не удалось».
  `--create-home` — домашняя папка (там будет `.ssh`), `--shell /bin/bash` — rsync и `bash -s` в `publish.sh` нужна оболочка.
- `install -d -m 700 -o deploy -g deploy папка` — создать папку **сразу** с владельцем и правами.
  Одна команда вместо `mkdir` + `chown` + `chmod`, и нет промежутка, когда папка существует с неправильными правами.
- `grep -qxF ключ файл || echo ключ >> файл` — дописать ключ, только если такой строки ещё нет:
  `-q` — ничего не печатать, `-x` — совпадение всей строки, `-F` — искать как текст, а не регулярное выражение
  (в ключе есть `+` и `/`). `2>/dev/null` — при первом запуске файла нет, и ошибку `grep` прятать нормально.
  **Без этой проверки** каждый повторный запуск скрипта дописывал бы дубль.
- `chmod 600 authorized_keys` и `700 .ssh` — sshd игнорирует `authorized_keys`, если их может менять кто-то ещё (`StrictModes`).

**Что может пользователь `deploy`.** Это обычный пользователь без `sudo`: писать он может в свою домашнюю папку
и в `/var/www/site`. Систему он не сломает, но может запускать любые команды. Ужесточить можно в `authorized_keys`:
`restrict,command="rrsync /var/www/site" ssh-ed25519 AAAA…` разрешит этому ключу только rsync в одну папку.
Но тогда перестанет работать вторая часть `publish.sh` (переключение симлинка через `bash -s`), и её
пришлось бы переделать — например, в отдельную команду, разрешённую через `command=`.

```bash
install -d -o deploy -g deploy /var/www/site /var/www/site/releases
if [ ! -e /var/www/site/current ]; then
  install -d -o deploy -g deploy /var/www/site/releases/initial
  echo '<!doctype html><meta charset="utf-8"><title>Скоро</title><p>Сайт скоро появится.' \
    > /var/www/site/releases/initial/index.html
  chown deploy:deploy /var/www/site/releases/initial/index.html
  ln -sfn releases/initial /var/www/site/current
  chown -h deploy:deploy /var/www/site/current
fi
```

Готовит модель выпусков (глава 11): `releases/` — папки сборок, `current` — симлинк на активную.

- Начальный выпуск `initial` с заглушкой «Сайт скоро появится». Зачем: Caddy сразу есть что отдавать,
  а первый `publish.sh` может использовать `current/` как основу для `--link-dest`.
- `ln -sfn releases/initial current` — **относительная** ссылка. Работает, даже если всю `/var/www/site` перенести.
- `chown -h` — сменить владельца **самого симлинка**, а не папки, на которую он указывает. Без `-h` команда
  прошла бы по ссылке к `releases/initial`, а сам симлинк остался бы принадлежать root. Заменить его `deploy`
  смог бы и так — замена делается переименованием, а оно зависит от прав на папку `/var/www/site` (глава 11), —
  но единый владелец у всего в `/var/www/site` избавляет от сюрпризов.
- Права по умолчанию у папок — 755, у файлов — 644: пользователь `caddy` может читать, но не писать.
  Это важно: даже взломав Caddy, файлы сайта не подменить.

```bash
SCRIPT_DIR=$(cd "$(dirname "$0")" && pwd)
sed "s/example\.com/$DOMAIN/g" "$SCRIPT_DIR/Caddyfile" > /etc/caddy/Caddyfile
install -m 755 "$SCRIPT_DIR/rollback.sh" /usr/local/bin/site-rollback
caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy || systemctl restart caddy
```

- `SCRIPT_DIR` — папка, где лежит сам скрипт. Так `Caddyfile` и `rollback.sh` находятся, откуда бы скрипт ни запустили.
- `sed "s/example\.com/$DOMAIN/g"` — подставить домен вместо `example.com` во всём файле (`g` — все вхождения в строке).
  Точка экранирована: без `\.` она значила бы «любой символ». Заодно `www.example.com` становится `www.ваш-домен`.
- `install -m 755 rollback.sh /usr/local/bin/site-rollback` — скопировать скрипт отката как команду `site-rollback`
  с правом на запуск.
- `caddy validate` — проверить конфиг **до** применения. Ошибка в Caddyfile остановит скрипт (`set -e`) раньше,
  чем сломает работающий сервер.
- `systemctl reload caddy` — применить конфиг **без остановки**: Caddy подхватывает новый конфиг на лету, открытые
  соединения не рвутся. `|| restart` — на случай, если служба ещё не запущена (reload работает только у запущенной).

```bash
echo "  ssh-keyscan -t ed25519 $(hostname -I | awk '{print $1}')"
```

Подсказка, как получить отпечаток сервера для секрета `DEPLOY_KNOWN_HOSTS` (глава 9). `hostname -I` — все IP
сервера, `awk '{print $1}'` — первый. Запускать `ssh-keyscan` нужно **на своём компьютере**: так вы получаете ключ
того сервера, к которому подключаетесь, а сверить его можно с `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` на сервере.

## Как сделано здесь: `deploy/Caddyfile`

```caddyfile
# /etc/caddy/Caddyfile — HTTPS-сертификат Caddy получает сам.
# Замените example.com на свой домен (и www, если нужен).

www.example.com {
	redir https://example.com{uri} permanent
}

example.com {
	root * /var/www/site/current
	encode zstd gzip

	header {
		Strict-Transport-Security "max-age=31536000"
		X-Content-Type-Options nosniff
		Referrer-Policy strict-origin-when-cross-origin
		-Server
	}

	# Файлы с хешем в имени (CSS, обработанные картинки) не меняются — кешируем надолго.
	@fingerprinted path_regexp \.[0-9a-f]{16,}\.\w+$|_hu_[0-9a-f]+
	header @fingerprinted Cache-Control "public, max-age=31536000, immutable"

	header /admin/* {
		Cache-Control no-store
		X-Robots-Tag noindex
	}

	file_server

	handle_errors 404 {
		rewrite * /404.html
		file_server
	}
}
```

### Разбор

**Блоки сайтов.** `example.com { … }` — всё, что относится к этому адресу. Указан домен, а не порт — и это
включает **автоматический HTTPS**:

1. При запуске Caddy обращается к Let's Encrypt (или ZeroSSL) по протоколу ACME и получает сертификат.
   Чтобы удостоверяющий центр убедился, что домен ваш, он стучится на этот домен по порту 80 (HTTP-01)
   или 443 (TLS-ALPN-01).
2. Caddy сам продлевает сертификат заранее, до истечения.
3. Запросы на `http://` автоматически перенаправляются на `https://`.

Что для этого нужно: DNS домена указывает на сервер, порты **80 и 443** открыты, других веб-серверов на них нет.
Если что-то не так, Caddy пишет причину в журнал: `journalctl -u caddy -e`.

**А если иначе:** `:80 { … }` вместо домена — только HTTP, без сертификата. Годится для проверки на голом IP.
`localhost { … }` — Caddy выпустит сертификат своим локальным центром — удобно для разработки.

```caddyfile
www.example.com {
	redir https://example.com{uri} permanent
}
```

`www.домен` получает свой сертификат и отвечает редиректом на основной домен. `{uri}` — путь и параметры запроса,
чтобы `www.домен/posts/x/` вёл на `домен/posts/x/`, а не на главную. `permanent` — код 301: поисковики запомнят
основной адрес. Есть `temporary` (302) и явные коды, например `308`.

**А если иначе:** без этого блока `www.домен` не откроется вовсе (если у него есть DNS-запись — посетитель
увидит ошибку TLS). Если `www` не нужен, блок можно удалить вместе с DNS-записью. Обратный вариант — основной `www`:
поменять домены местами.

```caddyfile
	root * /var/www/site/current
```

Корень сайта. `*` — матчер «для всех запросов». Указывает на **симлинк** `current`: после переключения выпуска
(глава 11) Caddy сразу отдаёт новые файлы, перезапускать его не нужно.

```caddyfile
	encode zstd gzip
```

Сжимать ответы: браузеру отдаётся первый поддерживаемый им вариант — zstd (новее и эффективнее), иначе gzip.
HTML и CSS сжимаются в 3–5 раз. Картинки WebP уже сжаты, Caddy их не трогает. **Без строки** все текстовые файлы
шли бы несжатыми.

```caddyfile
	header {
		Strict-Transport-Security "max-age=31536000"
		X-Content-Type-Options nosniff
		Referrer-Policy strict-origin-when-cross-origin
		-Server
	}
```

Заголовки на все ответы:

- **`Strict-Transport-Security` (HSTS)** — браузер запомнит на год (31 536 000 секунд): «на этот сайт — только HTTPS».
  Даже если пользователь наберёт `http://`, браузер сам пойдёт по HTTPS, и перехватить первый запрос нельзя.
  Расширения: `; includeSubDomains` — для всех поддоменов (осторожно: сломает поддомены без HTTPS), `; preload` —
  заявка на включение домена в список, встроенный в браузеры. Начинать стоит с малого `max-age`: отменить
  HSTS у посетителей, которые уже его запомнили, нельзя до истечения срока.
- **`X-Content-Type-Options nosniff`** — браузер не будет «угадывать» тип файла. Загруженный файл `.txt`
  с HTML внутри не выполнится как страница.
- **`Referrer-Policy strict-origin-when-cross-origin`** — при переходе с вашего сайта на чужой передаётся только домен,
  а не полный адрес страницы. Строже — `no-referrer`, мягче — `unsafe-url` (не надо).
- **`-Server`** — минус перед именем удаляет заголовок. Caddy по умолчанию пишет `Server: Caddy`; лишняя информация
  для сканеров уязвимостей.

**Где ещё пригодится:** `Content-Security-Policy` — список разрешённых источников скриптов и стилей. Сайту без JS
подошла бы очень строгая политика (`default-src 'self'`), но админке нужен скрипт с unpkg и запросы к GitHub API, —
поэтому для `/admin/*` пришлось бы задать отдельную, мягче.

```caddyfile
	# Файлы с хешем в имени (CSS, обработанные картинки) не меняются — кешируем надолго.
	@fingerprinted path_regexp \.[0-9a-f]{16,}\.\w+$|_hu_[0-9a-f]+
	header @fingerprinted Cache-Control "public, max-age=31536000, immutable"
```

- **`@fingerprinted`** — *именованный матчер*: набор условий с именем, который потом подставляют в директивы.
- **`path_regexp`** — путь подходит под регулярное выражение. Две альтернативы через `|`:
  - `\.[0-9a-f]{16,}\.\w+$` — точка, 16+ шестнадцатеричных символов, точка, расширение в конце: это CSS после
    `fingerprint` (глава 6) — `site.min.a2d27922….css`;
  - `_hu_[0-9a-f]+` — так Hugo называет обработанные картинки: `cover_hu_c7a3dd2baceef45e.webp` (глава 5).
- **`Cache-Control: public, max-age=31536000, immutable`** — браузер и промежуточные кеши хранят файл год
  и даже не переспрашивают сервер. Это безопасно, потому что имя файла зависит от содержимого: изменится CSS —
  изменится хеш — HTML сошлётся на новый файл.

**Проверено:** на собранном сайте выражение отбирает ровно четыре файла — CSS и три `_hu_`-картинки.
HTML, `index.xml`, `robots.txt`, исходные `cover.jpg`/`chart.png` и стили KaTeX под него не попадают:
у них имя постоянное, и вечный кеш для них был бы ошибкой — посетители не увидели бы обновлений.

**А если иначе:** `header Cache-Control "max-age=31536000"` для всего сайта — новые записи не появлялись бы
у вернувшихся посетителей до года. Без правила вовсе — браузер каждый раз переспрашивает про CSS и картинки
(ответ `304 Not Modified` быстрый, но это лишний запрос на каждый файл).

```caddyfile
	header /admin/* {
		Cache-Control no-store
		X-Robots-Tag noindex
	}
```

- Путь-матчер `/admin/*` — всё внутри админки.
- `Cache-Control no-store` — не кешировать вовсе. Иначе после правки `config.yml` браузер мог бы показывать
  старую форму с прежними полями.
- `X-Robots-Tag noindex` — запрет индексации заголовком (действует и на `config.yml`, где нет `<meta>`).

```caddyfile
	file_server
```

Отдавать файлы из `root`. Для пути, оканчивающегося на `/`, отдаётся `index.html` в этой папке — поэтому
адреса вида `/posts/kak-nachinalsya-proekt/` работают без `.html`. **Без `file_server`** Caddy отвечал бы
пустым `200` на всё: директивы выше только добавляют заголовки, а отдавать файл — работа этой.

```caddyfile
	handle_errors 404 {
		rewrite * /404.html
		file_server
	}
```

Когда файл не найден (404), отдать вместо пустой ошибки страницу `/404.html` — её собирает Hugo из `layouts/404.html`.
`rewrite` меняет путь внутри сервера, адрес в браузере остаётся прежним, а код ответа остаётся 404 —
поисковики не примут страницу ошибки за настоящую. Число `404` после `handle_errors` ограничивает блок только этой ошибкой.

**А если иначе:** без блока посетитель увидит пустую страницу. `redir * /` вместо `rewrite` — «мягкий 404»:
всё несуществующее ведёт на главную с кодом 302, это путает и людей, и поисковики.

## Безопасность сервера: что добавить

Скрипт настраивает только сайт. На реальном сервере стоит сделать ещё (вручную, один раз):

- **Запретить вход по паролю.** В `/etc/ssh/sshd_config`: `PasswordAuthentication no`, `PermitRootLogin prohibit-password`,
  затем `systemctl reload ssh`. Сначала убедитесь, что вход по ключу работает, — иначе закроете дверь перед собой.
- **Файрвол.** `ufw allow OpenSSH`, `ufw allow 80`, `ufw allow 443`, `ufw enable`. Или файрвол в панели хостинга
  (у Hetzner — Cloud Firewall). Порты 80 и 443 нужны оба: 80 — для выпуска сертификата и редиректа на HTTPS.
- **Автоматические обновления безопасности.** `apt-get install unattended-upgrades` и
  `dpkg-reconfigure -plow unattended-upgrades`.
- **Резервная копия не нужна.** Всё, что есть на сервере, восстанавливается из репозитория: заново запустить
  `setup-server.sh` и workflow. Это прямое следствие статического сайта.

## Альтернатива: nginx + certbot

То же самое на nginx потребовало бы:

- установить `nginx` и `certbot`, получить сертификат командой `certbot --nginx -d домен -d www.домен`
  и следить, чтобы продление (таймер certbot) работало;
- описать `server` на порт 80 с редиректом, `server` на 443 с путями к сертификату и ключу,
  `ssl_protocols`, `gzip on` с перечислением типов, `location ~* ...` для кеша, `add_header` для каждого заголовка
  (с оговоркой, что `add_header` во вложенном `location` отменяет заголовки родителя), `error_page 404 /404.html`.

Это 40–60 строк против 30 у Caddy и одна служба вместо двух. nginx выбирают, когда он уже есть на сервере
или нужны его особые возможности; для одного статического сайта Caddy проще.

## Где ещё пригодится

- Несколько сайтов на одном сервере — несколько блоков с разными доменами в одном Caddyfile; каждый получит свой сертификат.
- `reverse_proxy localhost:3000` вместо `file_server` — Caddy станет HTTPS-«фасадом» для любого приложения.
- `basic_auth` — закрыть паролем, например, превью-поддомен для PR.
- `log { output file /var/log/caddy/site.log }` — журнал запросов, если хочется простой статистики без счётчиков на сайте.

## Упражнения

1. Поставьте Caddy локально и запустите `caddy adapt --config deploy/Caddyfile` — увидите, во что Caddyfile
   превращается во внутреннем JSON-формате. Найдите там матчер `@fingerprinted`.
2. Замените в локальной копии Caddyfile домен на `localhost`, `root` — на папку `public/` после `make build`,
   запустите `caddy run` и проверьте заголовки: `curl -skI https://localhost/` и `curl -skI https://localhost/css/<файл>.css`.
3. Запросите несуществующую страницу `curl -skI https://localhost/net-takoy/`. Какой код ответа? Что будет с кодом,
   если заменить `rewrite` на `redir`?
4. Запустите `setup-server.sh` второй раз на том же сервере. Убедитесь, что в `authorized_keys` не появилось дубля.

## Итог

Сервер настраивается одним идемпотентным скриптом: ставит Caddy и rsync, создаёт пользователя `deploy` с ключом
только для деплоя, готовит папки выпусков и кладёт Caddyfile с вашим доменом. Caddy сам получает и продлевает
HTTPS-сертификат, сжимает ответы, ставит заголовки безопасности, кеширует навсегда только файлы с хешем в имени
и показывает свою страницу 404. Всё, что на сервере, восстанавливается из репозитория.
